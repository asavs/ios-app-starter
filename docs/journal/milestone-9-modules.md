## 2026-10-19 — Onboarding module: gated page flow, completion by version, smoke test steps through it

- **Context:** Round-one module `Onboarding` (board task `ios-mod-onb`), the first module that depends on another (`Theme`). Tools: Xcode 26.6 and the iOS 26.5 simulator on the Mac, XcodeGen 2.46.0 through `scripts/generate-project.sh`, Swift 6 language mode.
- **Design:** Content (`OnboardingPage`), position rules (`OnboardingPager`, a plain value) and persistence (`OnboardingRecord`, the completed version in `UserDefaults`) are separate from the views so the rules are tested host-side. `OnboardingView` is a page-style `TabView` with Skip, Continue and a final call to action built from the theme's button styles; `.onboardingGate(pages:version:record:)` swaps the flow for its content once finished, keeping the decision in view state for the current launch. Completion is a version number rather than a flag so an app can show a revised flow by raising it. `UserDefaults` is the store because nothing here is secret; Keychain-backed values are the Settings module's job.
- **Decision (confirmed):** The required smoke test runs only `testWelcomeScreen`, which asserted the welcome text on launch; a fresh simulator now shows onboarding first. Rather than a second UI test, the smoke test launches with `-onboarding.completedVersion 0` (`UserDefaults` reads launch arguments ahead of stored values, so the flow shows even on a reused simulator), taps `onboarding.next` while it exists, attaches a screenshot of the first page, and asserts the welcome text; with the module disabled the button never appears and the test asserts the welcome text directly. The launch-performance test passes `1` to measure the app, not the flow. Because the argument domain shadows the stored value, the gate keeps its decision in `@State` and the record only persists; otherwise finishing would not release the gate under the override.
- **Constraint (confirmed):** `UserDefaults` is not annotated `Sendable` in the macOS 26.5 SDK, so a `Sendable` struct holding one fails to compile under Swift 6; `OnboardingRecord` is `@unchecked Sendable` with the documented thread-safety as justification. Swift Testing's `#expect` captures its argument immutably, so a `mutating` call such as `pager.advance()` must be assigned to a `let` before the expectation.
- **Change:** `Modules/Onboarding/Sources` (`OnboardingPage`, `OnboardingPager`, `OnboardingRecord`, `OnboardingView`, `OnboardingGate`, `Elements/OnboardingPageView`), `Modules/Onboarding/Tests/OnboardingTests.swift` (9 Swift Testing tests), `Package.swift` product and targets (`Onboarding` depends on `Theme`), `project.yml` product line, regenerated project, `StarterAppApp` gating `ContentView` under `#if canImport(Onboarding)`, the UI smoke test, and the Available modules section in `docs/modules.md`.
- **Verification:** `swift test` passed (18 tests across three modules). `test-module.sh Onboarding` on the iOS 26.5 simulator: 9/9 passed through the `StarterModules-Package` scheme. `test-ios.sh` on the same simulator: the welcome-screen smoke test passed in 15 s, and its `onboarding-first-page` screenshot shows the Welcome page with Skip, page dots and the themed Continue button before the `welcome-screen` screenshot shows the greeting. `check-modules.py` reports all three modules enabled for `project.yml` and all three disabled for the `no-modules` overlay, whose generated project built for the simulator (`BUILD SUCCEEDED`). Portable tests (`unittest discover`, `check-configurations.py`) pass. The hosted Xcode 27 lane runs on the pull request.
- **Limits and next:** The module tests cover the rules and public initializers, not rendering or swiping; the app smoke test is the only check that the flow appears and finishes. `OnboardingPage` carries text only; localization and images beyond SF Symbols are an app's choice for now. Remaining round-one modules: settings (persisting `AppearancePreference` and exposing `OnboardingRecord.reset()`), icon pipeline; then shipping round one to the phone.

## 2026-10-19 — Theme module: tokens in the environment, shared elements, no UIKit in the tested core

- **Context:** Round-one module `Theme` (board task `ios-mod-theme`), the second product of `StarterModules` after the seed. Tools: Xcode 26.6 and the iOS 26.5 simulator on the Mac, XcodeGen 2.46.0 through `scripts/generate-project.sh`, Swift 6 language mode.
- **Design:** One `AppTheme` value (colors, spacing, radii, typography) in a SwiftUI `EnvironmentKey`, defaulting to `AppTheme.standard`, which follows the system (dynamic colors, asset accent, Dynamic Type) so an app that never customizes still adapts to dark mode and text size. Elements read the environment rather than taking a theme parameter, so one `.appTheme(_:)` at the root restyles every element. `AppearancePreference` is a `String`-backed `Codable` enum with stable keys so the Settings module can persist it. Nothing in the tokens imports UIKit; the two dynamic background colors are chosen with `#if canImport(UIKit)` / `canImport(AppKit)` so the package keeps compiling for macOS and `swift test` stays a fast host-side check.
- **Failure (confirmed):** `scripts/test-module.sh Theme` failed with "The workspace named \"ios-app-starter\" does not contain a scheme named \"StarterModules\"". With one product, Xcode derives a single scheme named after the package; with two or more it derives one scheme per product plus `StarterModules-Package`, and the per-product schemes have no test action (`Scheme Theme is not currently configured for the test action`, exit 66). Fix: the script reads `xcodebuild -list -json` and runs `StarterModules-Package` (falling back to `StarterModules`) with `-only-testing:<Module>Tests`. The required CI matrix runs this package-wide scheme once per module.
- **Change:** `Modules/Theme/Sources` (`AppTheme`, `ThemeEnvironment`, `AppearancePreference`, `Elements/ButtonStyles`, `ThemedCard`, `EmptyStateView`), `Modules/Theme/Tests/ThemeTests.swift` (8 Swift Testing tests), `Package.swift` product and targets, `project.yml` product line, regenerated project, `ContentView` build details on a `ThemedCard` under `#if canImport(Theme)`, and the Available modules section in `docs/modules.md`.
- **Verification:** `swift test` passed (9 tests, both modules). `test-module.sh Theme` on the iOS 26.5 simulator: 8/8 passed through the `StarterModules-Package` scheme. `test-ios.sh` on the same simulator: welcome-screen smoke test 1/1 passed, and its screenshot shows the build details on the themed card. `check-modules.py` reports both modules enabled for `project.yml` and both disabled for the `no-modules` overlay, whose generated project built for the simulator (`BUILD SUCCEEDED`). Portable tests (`unittest discover`, `check-configurations.py`) pass. The hosted Xcode 27 lane runs on the pull request.
- **Limits and next:** The element tests check public initializers and token invariants, not rendering; snapshot or UI checks of the elements can be added later. `#Preview` blocks in the package are for Xcode users and are not exercised in CI. Remaining round-one modules: onboarding (unblocked by this), settings and icon pipeline.

## 2026-10-19 — Module mechanism: one root package, products per module, tags for apps

- **Context:** Master plan step 5 asks for modules that live here as tagged Swift packages, a template that depends on them by path, and apps that depend on tagged versions. Tools: Xcode 26.6 on the Mac (CI stays on Xcode 27.0), XcodeGen 2.46.0, Swift 6.3.3 host toolchain, `swift-tools-version: 6.0` so the Xcode 16.2 compatibility lane still parses the manifest.
- **Constraint (confirmed):** Swift Package Manager resolves a git dependency only from the repository's root manifest. A scratch repository whose root package depended on a nested `Nested/Package.swift` by path, tagged `1.0.0` and consumed by URL, failed resolution with "package 'lib' is required using a stable-version but 'lib' depends on an unstable-version package 'nested'". So the mechanism is one root `Package.swift` with one library product per `Modules/<Name>/` folder, not nested packages. Per-module versioning would need separate repositories or subtree mirrors; not needed for round one.
- **Constraint (confirmed):** XcodeGen writes a top-level spec's `packages.path` verbatim relative to the generated project directory (`StarterApp/`), so `path: .` produced a reference to `StarterApp/Package.swift` and `path: ..` is right. For an included spec it rebases the value relative to the including file: `examples/pocket-notes.yml` received `../..` and a probe spec in a temporary directory received an absolute path one directory above the repository. Fix: every overlay repeats the package block, the probes pass the absolute repository path, and `check-modules.py` rejects a reference that does not resolve to this repository with the fix named.
- **Change:** `Package.swift` (`StarterModules`, iOS 17, macOS 14 for host-side `swift test` only), seed module `TemplateVersion` whose `modules` constant equals the tag and appears as "Modules 0.1.0" on the welcome screen under `#if canImport(TemplateVersion)`; `project.yml` gains the path package and one product line; `examples/no-modules.yml` disables everything; `scripts/check-modules.py` (manifest layout from `swift package dump-package`, enablement and package path from the generated project, package platform at or below the app minimum, `modules.json` output) runs in the required `iOS` lane; `scripts/test-module.sh <Name>` runs one module's tests on the simulator through the single `StarterModules` scheme; `scripts/tag-modules.py` creates the semantic-version tag after checking the constant, clean tree, `main`, `origin/main` and tag uniqueness; `docs/modules.md` is the guide.
- **Verification:** `swift test` passed (1 test). `test-module.sh TemplateVersion` on the iOS 26.5 simulator: 1/1 passed with the standard `summary.md`. `test-ios.sh` on the same simulator: welcome-screen smoke test passed and its screenshot shows the "Modules 0.1.0" line. The `no-modules` overlay project built for the simulator. `check-configuration.py` passed; the `missing-identifier` probe still rejects as before. 17 new portable tests (layout, project references, tagging) pass alongside the existing suite. Tag consumption by URL was verified against a scratch clone tagged `0.1.0` (see the task comment); no tag has been pushed to the real repository yet.
- **Limits and next:** Xcode exposes one scheme for the package, so a per-module run builds every test target and filters with `-only-testing`; fine while the library is small. The hosted runner has not yet run the new lane step; the pull request is the proof. Remaining board items: first tag `0.1.0` from `main` after merge, the four round-one modules, per-module and no-modules CI lanes, package dependency caching.
