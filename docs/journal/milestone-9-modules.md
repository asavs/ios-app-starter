## 2026-10-20 — Onboarding choice step and TipKit contextual tips; toolbar popovers do not show on iOS 26

- **Context:** Task `ios-s5.5`, the follow-up to the step model (PR #64). Tools: Xcode 26.6 and the iOS 26.5 simulator on the Mac; CI on Xcode 27.0. The choice step is included on the owner's decision even though the research favours it only when the answer changes the product, which the template's copy says.
- **Change:** `OnboardingStep.choice(OnboardingChoice)`: one question, `.single` or `.multiple`, options with an optional symbol, `requiresAnswer`, `initialSelection`, and `onAnswer`, which receives the answer (option identifiers in option order) every time it changes, so the host has it whether the user continues, swipes or skips. With `requiresAnswer` the Continue button is disabled and `OnboardingView.reachableIndex` stops a swipe at the unanswered step. The contextual tips wrapper lives in the Onboarding module: `ContextualTips.configure()` (reset requested by `resetOnNextLaunch()` or `-tips.reset YES`, test overrides `-tips.testing showAll|hideAll`), `ContextualTip` (a value-described `Tip` whose rule waits for `ContextualTips.isEligible`, which the onboarding gate turns off while its flow shows), `ContextualTipSequence` (a `TipGroup(.ordered)` on iOS 18, the first tip only on iOS 17), `.contextualTip(_:in:)` for popovers and `ContextualTipView` for inline tips. The template flow becomes welcome, choice, tour, primer at gate version 3; the welcome screen shows the answer ("Building: ...") and two tips in order, Settings inline and then the tour popover on the replay button; Settings gains "Show tips again on next launch".
- **Failures (confirmed):** (1) Before iOS 26 the SDK's `popoverTip` overloads for an optional tip are gated per release (18.0 to 18.4, 18.4 on), and the compiler resolves a call to the unconditional-looking iOS 26 overload, failing with "only available in iOS 26.0 or newer" even inside an `else` of `#available(iOS 26, *)`. A concrete, non-optional tip resolves to the generic iOS 17 overload, so the wrapper uses that below iOS 26 and drops the popover when there is no tip. (2) A `popoverTip` on the toolbar's Settings button (a `NavigationLink`, and still after changing it to a `Button`) never appeared on the iOS 26.5 simulator, even with `showAllTipsForTesting`, while the same sequence anchored on in-content views showed. Workaround: the Settings tip is inline (`ContextualTipView`) above the greeting. (3) Static helpers on the `View` struct are main-actor isolated, and calling them from a nonisolated Swift Testing test crashed the test process with `dispatch_assert_queue` under parallel runs; the pure rules are `nonisolated`.
- **Verification:** `swift test`: 42 tests pass (11 new in Onboarding: single and multiple selection, answer order, initial selection, required-answer gating and swipe stop, the template's answer reaching the host, tip content, sequence anchoring, reset flag). `test-ios.sh` on the iOS 26.5 simulator: 5/5 UI tests pass; `testOnboardingSteps` picks two answers, clears one, asserts "Building: A product to sell" on the welcome screen, then the Settings tip, its Close, and the tour popover, with screenshots `onboarding-choice`, `onboarding-tip-settings` and `onboarding-tip-tour`. Other UI tests pass `-tips.testing hideAll` so no tip covers what they check.
- **Remaining:** The hosted Xcode 27 lane is the first run on iOS 27; whether toolbar popovers work there is unchecked. The iOS 17 ordered-group fallback (first tip only) has no runtime test, since no iOS 17 simulator runs in the required lanes. VoiceOver on a device is pending.

## 2026-10-19 — Template mark: a hand-authored Icon Composer document replaces the flat PNG

- **Context:** Task `ios-mark` (issue #25), chosen live with the owner by putting drafts on his iPhone. Xcode 26.6 locally (actool 26.6, Icon Composer 1.6); CI builds with Xcode 27.0.
- **Decision:** The template's icon is an empty blueprint sheet: blue paper, a grid, a dashed construction circle, dash-dot centre lines, a dimension line, and a radius at 12 o'clock with the angle swept to it from 7 o'clock. It reads as a draft of an app rather than a finished product. The sweep is a nod to TestFlight's propeller: sampling its icon showed each blade trails a clockwise wake that brightens toward the blade, so the slice fades in toward the radius. Only the idea is borrowed; no TestFlight geometry or artwork is used. Rejected drafts: a glass `< • >` motif, an outlined letter, a paper plane, dashed motifs, and an arc arrow on the angle.
- **Change:** `StarterApp/StarterApp/AppIcon.icon` is written the way Icon Composer saves a document: four flat white SVG layers (`grid`, `construction`, `sweep`, `radius`) and an `icon.json` that sets everything else: an `automatic-gradient` background with a dark specialization, Liquid Glass on the grid, construction and radius layers with per-group specular highlights, shadows (`layer-color` under the radius), translucency, blur material and combined lighting, and the sweep's fade as a layer `linear-gradient` fill with alpha and `plus-lighter` blending. The sweep stays out of glass: a glass wedge shows a hard rim along its 7 o'clock edge that defeats the fade. The document format has no angular gradient, so the fade is linear. Keys are sorted with `" : "` separators, as Icon Composer writes them. The `AppIcon.appiconset`, its PNG, `scripts/generate-starter-icon.py` and `design/starter-icon.svg` are removed: the document is the source and edits by hand on any platform. XcodeGen 2.46.0 picks up the `.icon` from the target's sources as a `wrapper.icon` resource without manifest changes.
- **Discovery (confirmed):** `actool` compiles an `.icon` alone into both the iOS 26 layered icon and the `AppIcon60x60@2x.png`/`AppIcon76x76@2x~ipad.png` fallbacks for the iOS 17 minimum, so `scripts/testflight-release.py`'s compiled-icon check still holds.
- **Discovery (confirmed):** Without a dark fill specialization, the Dark rendition turned the background black and filled the dashed circle's interior with the light blue; an explicit dark `automatic-gradient` fixes it. Icon Composer ships a renderer, `Icon Composer.app/Contents/Executables/ictool`, that exports any rendition (`Default`, `Dark`, `TintedLight`, …) at any size, the quickest check at 60 px without a device; it reports a malformed `icon.json` only as "The data couldn't be read because it isn't in the correct format." NSImage on macOS rendered these SVGs as solid black.
- **Verification:** Installed with `scripts/run-on-device.sh` (`starter-app-demo`, `IOS_SIGNING_KEYCHAIN` set to the login keychain, as in the milestone 8 entry) and reviewed by the owner on the home screen; renditions checked with `ictool`. The built app contains the fallback PNGs and `CFBundleIconName = AppIcon`.

## 2026-10-20 — Onboarding steps: welcome sheet and permission primer as opt-in step kinds

- **Context:** Board task `ios-s5.4`, decided with the owner after trying the module on his phone: as a template the module should be comprehensive, with every well-founded piece opt-in. Tools: Xcode 26.6 and the iOS 26.5 simulator on the Mac, Swift 6 language mode; the hosted lane is Xcode 27.0.
- **Research (sources on the board):** The HIG wants onboarding fast, optional, skippable and never re-shown, prefers context-specific tips to a flow, delays sign-in and asks for permissions at first use with a one-button pre-alert screen. The Nielsen Norman Group found card-deck tutorials gave no gain in success or speed and made tasks feel harder. Well-regarded apps (Things, Bear, Flighty, Overcast) seed content or use an empty state instead of a tour. Liquid Glass belongs on the control layer, not content.
- **Design:** `OnboardingStep` (id, `Kind`, `allowsSkip`, `continueTitle`) replaces fixed pages; kinds are `welcome(WelcomeContent)` with `WelcomeFeature` rows, `page(OnboardingPage)`, `permission(PermissionPrimer)` and `custom`. Permission primers hide Skip by default and run a `PermissionRequesting` requester on Continue (`NotificationPermission` real, `FakePermission` for tests, `PermissionOverride.resolve(real:)` choosing by the `-onboarding.permissions` launch argument). The Continue button is `.glassProminent` behind `#available(iOS 26, macOS 26, *)` and `.primary` before. The `pages:` initializers remain as wrappers. The template flow is one of each kind and the gate version went from 1 to 2 so existing installs see it once.
- **Constraints (confirmed):** `UNAuthorizationOptions` is stored as its raw value so the requester is `Sendable` without an unchecked conformance. A `custom` step holds a `@MainActor @Sendable () -> AnyView` builder, the one type-erased spot, so the step array stays `Sendable` for a `static let`. Step containers use `.accessibilityElement(children: .contain)` so `onboarding.step.<id>` is reachable as an XCUI `otherElement` without flattening the rows inside.
- **Change:** `Modules/Onboarding/Sources` (`OnboardingStep`, `CustomStepContent`, `WelcomeContent`, `WelcomeFeature`, `PermissionPrimer`, `PermissionRequesting`, `PermissionOutcome`, `NotificationPermission`, `FakePermission`, `PermissionOverride`, `Elements/WelcomeStepView`, `Elements/WelcomeFeatureRow`, `Elements/PermissionStepView`, `Elements/OnboardingContinueButton`; `OnboardingView` and `OnboardingGate` rewritten over steps), six new module tests, `StarterAppApp` on `templateDefaults` steps at version 2, `testOnboardingSteps` in the UI target with three screenshots and the smoke test passing the permission override, and the Onboarding section of `docs/modules.md`.
- **Verification:** see the pull request for the simulator and hosted results; `swift test` passed host-side (33 tests across four modules).
- **Limits and next:** The flow stays swipeable past a primer, which counts as declining to ask; the system alert is never forced. Rendering is checked only by the UI test screenshots. Follow-ups on the board: choice step and TipKit tips (`ios-s5.5`), Settings "Show introduction again" (`ios-s5.6`), sign-in module (`ios-s5.1`).

## 2026-10-19 — Onboarding module: gated page flow, completion by version, smoke test steps through it
