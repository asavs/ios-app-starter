## 2026-10-16 — Pull-request gate, documentation skips and repository settings script

- **Context:** Master plan step 4 and the agreed development loop. Four documentation-only merges earlier today each triggered the full three-app simulator matrix plus two archive preflights, and `main` had no ruleset, so "required check" was convention rather than enforcement. Auto-merge was unavailable for the same reason.
- **Change (`ios.yml`):** A `changes` job classifies each pull request: drafts and documentation-only changes (paths under `docs/`, root `*.md`, `LICENSE`) skip the simulator. Pull requests test the `starter` configuration only; pushes to `main` keep all three. A new `ios-gate` job is the single required check: it passes when the lane passed or the change was documentation-only, and fails for drafts, failed, cancelled or missing lanes, so a skipped job can never satisfy a required check. The pull-request trigger now includes `ready_for_review` so marking a draft ready re-runs the gate. Signing and TestFlight preflights ignore documentation paths on pull requests; they are not required checks.
- **Change (`scripts/configure-github-repo.py`):** Dry run shows current versus intended repository settings; `--apply` changes only differing ones: auto-merge on, delete head branches after merge, secret scanning and push protection on, allowed actions restricted to GitHub-owned and verified creators, workflow approval for all fork contributors, and a default-branch ruleset requiring a pull request plus the `ios-gate` and three `portable (...)` checks, with no bypass actors. The script exists so adopters apply the same posture to repositories created from the template.
- **Verification:** YAML parsed; checked for job-level `runner.*` references. The matrix expression was emulated for pull request, push, dispatch-all and dispatch-single cases. The dry run against this repository listed eight pending changes. The settings themselves were applied by the owner, not by an agent: the permission classifier treats ruleset creation as a permission grant, which is the correct boundary. Hosted verification is the pull request carrying this change, which must produce `ios-gate` and pass it.
- **Limits:** Required-check contexts must appear at least once before GitHub shows them as satisfiable; the first pull request after the ruleset is the proof. `review_ci.py` reads artifacts, not job names, so it is unaffected; the README now describes the `starter`-only pull-request lane.
