## 2026-10-19 — Cold and warm CI cache measurements

- **Context:** Master plan step 4 called for measuring before changing build caches. The pinned public tool downloads (XcodeGen and App Store Connect CLI) already use verified Actions caches; simulator DerivedData is intentionally fresh per run. Tools: GitHub Actions runner step timestamps and logs; current `main` run `39323984923` at `ba593d4`.
- **Cold evidence:** In the cache-seeding run [37875269100](https://github.com/asavs/ios-app-starter/actions/runs/37875269100), XcodeGen's macOS cache missed and its verified archive download completed about 4.5 seconds after the miss. The Ubuntu `asc` cache missed and the verified binary download completed about 0.6 seconds after the miss. Windows and macOS `asc` were already cache hits in that run, so this was not a fully cold matrix.
- **Warm evidence:** The next run [37875337210](https://github.com/asavs/ios-app-starter/actions/runs/37875337210) reported hits for XcodeGen and `asc` on macOS, Windows and Linux. Cache restore steps took about 0.3–2 seconds; the cache action steps round to 0–3 seconds in GitHub's step timestamps. Cached payloads were checksum-verified before use.
- **Current lane baseline:** The latest three-app `main` run [39323984923](https://github.com/asavs/ios-app-starter/actions/runs/39323984923) passed all configurations. XcodeGen cache steps took 1–2 seconds per app. Simulator preparation took 62–100 seconds, and build/test took 247–564 seconds per app; the workflow ran from 21:00:14Z to 21:15:58Z (15m44s). Queueing and concurrent-runner variation are included in the workflow wall time, not attributable to caching.
- **Decision and limits:** These observations confirm cache reuse and quantify its small step cost, but they do not establish a repeatable end-to-end speedup; cold misses were already short and the matrix was partly warm. Keep the verified public-download caches. Do not add DerivedData/compiler-output caching based on this evidence. The new root `Package.swift` has only local targets and no external package dependencies, so a Swift dependency cache has nothing to reuse yet. Measure again when external dependencies are introduced.

## 2026-10-17 — One-command approved delivery

- **Context:** Master plan step 4 asked for a single command from a fix on `main` to a build on the phone. The pieces existed (delivery workflow with `perform_upload`, environment gate, sanitized artifact, `review_ci.py --run`) but stringing them together meant four `gh` commands and the Actions UI, and `gh workflow run` does not return the run it created.
- **Change:** `scripts/deliver_testflight.py` proposes (branch head via `gh api repos/{repo}/branches/main`, newest iOS push run for that head, in-flight deliveries), dispatches, finds the new `workflow_dispatch` run by creation time against the IDs seen before dispatch, polls the run until it is `waiting` or `completed`, reads `pending_deployments` to confirm the gate is `apple-credentials` and whether the caller may approve, approves with `--approve` or prints the exact command, waits for completion, downloads only `testflight-delivery-<configuration>` and prints the four stage statuses and one verdict line. Timeouts return 3 with a `--run <id>` resume line. Reuses `review_ci.py` helpers (gh wrapper, run and artifact fetch, job lines).
- **Verification:** 118 portable tests (9 new: proposal, dispatched-run selection, timeout, pending deployment and approval command, fixed-field stage reading, verdicts including accepted-upload-then-failure, end-to-end with faked gh, approval-less path with double-dispatch refusal, CLI validation). Real dry run on this Mac named head `ad3f2a7` and its passing iOS push run 38982176418 and printed the dispatch command. The first live approved delivery is the acceptance; it also validates that the `dev-auto` group receives the build without assignment.
- **Limits:** The command polls GitHub from a shell, which is the allowed form of waiting; default cadence 30 s for up to 45 minutes. It cannot see Apple's processing beyond the workflow's single bounded read, so a `PROCESSING` result needs a later `review_ci.py --run` or a glance at TestFlight. `--approve` is a deliberate self-approval under the solo-owner policy; the environment still records who approved.

## 2026-10-16 — Human-step ledger and consent model

- **Context:** The owner's target onboarding is: clone, grant permissions once, sign in where required, walk away, come back to a template app on the phone. Today's work surfaced another "only you can click this" step (automatic distribution on the TestFlight `dev` group). Such steps were being mentioned in chat and lost.
- **Change:** Added `docs/human-steps.md`: every human step so far with its automation path (API/CLI, browser agent in the user's signed-in browser, configuration, or genuinely human) and six permission categories to be granted once at setup. The master plan's runbook step now starts from that consent checklist, and the standing rules require a ledger row the same day a step is called human. `AGENTS.md` instructs agents to add the row before handing a step to the user. The cloud-computer question is pinned to the live iMessage bridge milestone with decision criteria.
- **Findings worth acting on:** the TestFlight automatic-distribution switch is an API attribute (`hasAccessToAllBuilds` on beta group creation), so no browser is needed; the export-compliance question disappears for non-encrypting apps by shipping `ITSAppUsesNonExemptEncryption = NO` in the manifest; the `apple-credentials` environment can be created and protected through the GitHub API, so `configure-github-repo.py` can grow to cover it. App record creation remains the one step the public API does not offer (to verify), hence the browser-agent path.
- **Verification/limits:** Documentation only. API capabilities are stated from Apple's and GitHub's documented endpoints and must be confirmed when each row is implemented; none was exercised today.

## 2026-10-16 — Structured failure output and a deterministic screenshot (PR #38)

- **Context:** Master plan step 4. Reports named a failed test and quoted its message but not where it failed, compiler errors were only visible in the raw log excerpt, and runs kept no image on success. Fixtures: the deliberately failed run 38435651378 and the latest green `main` run, both downloaded and re-read with local Xcode 26.6 `xcresulttool`.
- **Findings:** `xcresulttool get test-results tests` carries a `Failure Message` node per failed case in the form `File.swift:LINE: message`; `export attachments` writes a `manifest.json` with per-test attachments. Xcode 26's default UI-test capture is a screen recording (a 4.4 MB `.mp4` on the failed run) and nothing on success, so a deterministic image needs the test itself to attach one. `xcodebuild` echoes assertion failures as `file:line: error: -[Suite test] : message`, which would otherwise be double-counted as compiler errors.
- **Change:** `report-tests.py` reads `tests.json` and `attachments/manifest.json` alongside `results.json`, reports each failed test with file, line, message, suite and target, extracts compiler errors with file, line and column, classifies the run as `passed`, `tests_failed`, `build_failed`, `setup_failed` or `unverified`, lists screenshots and notes other attachments, and writes `failures.json` next to `summary.md`. `test-ios.sh` exports both xcresulttool outputs after the summary, tolerating failure. The UI smoke test attaches a `keepAlways` screenshot named `welcome-screen` before asserting, so pass and fail both yield a PNG; the failure-probe needle in `ios.yml` follows the assertion to its new line. Both simulator workflows upload `failures.json`, `tests.json`, the manifest and PNGs; videos are listed, not uploaded.
- **Verification:** The failed fixture renders `Stage: tests_failed`, test `StarterAppUITests/testWelcomeScreen()`, location `StarterAppUITests.swift:31`, with no duplicate build error; the green fixture renders `passed`. A local run on the iOS 26.5 simulator passed 1/1 and produced a 72 KB `welcome-screen` PNG showing the welcome screen, listed under Screenshots. 71 portable tests pass, four new. Hosted proof is PR #38's own `starter` lane and the next controlled failure probe.
- **Limits:** Screenshots reach the artifact and the summary lists their paths; GitHub job summaries cannot embed local images, so viewing one means downloading the artifact (or an agent reading the PNG). Older toolchains in the compatibility matrix are expected to support both xcresulttool subcommands (Xcode 16+); if one does not, the run still reports from `results.json` and the log.

## 2026-10-16 — `review_ci.py` run and latest-run modes (PR #36)

- **Context:** Master plan step 4 asks for one command that answers "what happened on my last run". The review command only accepted `--pr`, so a `workflow_dispatch` run such as the compatibility matrix or the push run after a merge meant opening the Actions UI, and the matrix's `compatibility-report` and `ios-compat-*` artifacts were rejected by the strict allowlist. Implemented by a delegated agent on `codex/review-ci-run-mode`.
- **Change:** `--run <id>` reviews one run: workflow, event, branch, head SHA, status/conclusion with elapsed time, each job with policy-skip labelling and elapsed time, then recognized artifacts through the same sanitized path as PR mode. `--latest [--branch] [--workflow]` lists up to 20 runs for the checkout branch, picks the newest by creation time, says which it chose and why, then behaves like `--run`. The three modes are mutually exclusive; `--no-download` and `--require-checkout-head` work in all. The allowlist accepts `compatibility-report` and `ios-compat-*` (not `compatibility-plan` or `compat-inventory-*`); the report's verified-runtimes line and per-lane status, runtime, device, toolchain, runner and counts are printed, and lane artifacts gain a `lane-result.json` status line. Shared helpers replaced duplicated PR-mode code; PR output is unchanged except one footer sentence and name-sorted artifacts.
- **Verification:** 76 portable tests (67 before). Real read-only exercise: `--run 38974328806` listed nine jobs and the four verified runtimes with per-lane details and app identity; `--latest --branch main --workflow iOS --no-download` selected the newest `main` run and listed its artifacts without downloading.
- **Limits:** `--latest` prefers the newest run by creation time, so an in-progress run wins over an older finished one; no `--limit` flag. The checkout comparison is against the run head only. Compatibility evidence comes from the aggregate report when the `report` job ran, otherwise from per-lane files.

## 2026-10-16 — `run-on-device` inner loop for Macs (PR #37)

- **Context:** Master plan step 4: get a change onto a connected iPhone from a Mac without a commit, upload or TestFlight. Tooling: Xcode 26.6, `devicectl` 518.33 (JSON version 3). Implemented by a delegated agent on `codex/run-on-device`; the hosted Xcode 27 toolchain is unaffected.
- **Change:** `scripts/run-on-device.sh` regenerates the project from `IOS_CONFIGURATION`/`IOS_PROJECT_SPEC`, lists devices with `xcrun devicectl list devices --json-output` (the only devicectl output Apple declares stable for scripts), selects the single connected paired iPhone/iPad or requires `IOS_DEVICE`, builds Debug with `-allowProvisioningUpdates CODE_SIGN_STYLE=Automatic DEVELOPMENT_TEAM=<team>` (team from `IOS_DEVELOPMENT_TEAM`, else the generated project), installs with `devicectl device install app`, launches with `devicectl device process launch --terminate-existing`, and streams the console behind `IOS_DEVICE_CONSOLE=1`. `IOS_RUN_ON_DEVICE_DRY_RUN=1` prints every command for agent preview; `IOS_REGISTER_DEVICE=1` opts into device registration. Output goes to the gitignored `build/run-on-device/`. `scripts/device_selection.py` holds the testable logic.
- **Findings:** The devicectl JSON has no "connected" field; the table's "available" matched `connectionProperties.tunnelState != "unavailable"` (a reachable Wi-Fi phone reports `disconnected`), observed on this Mac rather than documented. `xcodebuild -showdestinations` identifies a physical device by UDID while devicectl prints a CoreDevice UUID, so the script passes the UDID to `-destination id=` and the CoreDevice identifier to `--device`. devicectl launch options must precede the bundle identifier or they are forwarded to the app.
- **Verification:** `bash -n`; 87 portable tests (20 new, including fixture-driven dry runs that need no xcrun or device). Real dry runs on this Mac with two paired phones (one reachable over Wi-Fi, one offline) selected the reachable iPhone 14 Pro on iOS 26.3, excluded the offline one, and printed commands matching the help text.
- **Limits:** No real build, install or launch yet: no development team was configured and no Apple sign-in, certificate or profile change was made. First use with automatic signing creates or refreshes a development profile for the team and device. The default `com.example.StarterApp` identifier may not be provisionable under an arbitrary team, so use the demo configuration or your own identifier. `--terminate-existing` carries Apple's "not supported on all platforms" caveat.

## 2026-10-16 — Pull-request gate, documentation skips and repository settings script

- **Context:** Master plan step 4 and the agreed development loop. Four documentation-only merges earlier today each triggered the full three-app simulator matrix plus two archive preflights, and `main` had no ruleset, so "required check" was convention rather than enforcement. Auto-merge was unavailable for the same reason.
- **Change (`ios.yml`):** A `changes` job classifies each pull request: drafts and documentation-only changes (paths under `docs/`, root `*.md`, `LICENSE`) skip the simulator. Pull requests test the `starter` configuration only; pushes to `main` keep all three. A new `ios-gate` job is the single required check: it passes when the lane passed or the change was documentation-only, and fails for drafts, failed, cancelled or missing lanes, so a skipped job can never satisfy a required check. The pull-request trigger now includes `ready_for_review` so marking a draft ready re-runs the gate. Signing and TestFlight preflights ignore documentation paths on pull requests; they are not required checks.
- **Change (`scripts/configure-github-repo.py`):** Dry run shows current versus intended repository settings; `--apply` changes only differing ones: auto-merge on, delete head branches after merge, secret scanning and push protection on, allowed actions restricted to GitHub-owned and verified creators, workflow approval for all fork contributors, and a default-branch ruleset requiring a pull request plus the `ios-gate` and three `portable (...)` checks, with no bypass actors. The script exists so adopters apply the same posture to repositories created from the template.
- **Verification:** YAML parsed; checked for job-level `runner.*` references. The matrix expression was emulated for pull request, push, dispatch-all and dispatch-single cases. The dry run against this repository listed eight pending changes. The settings themselves were applied by the owner, not by an agent: the permission classifier treats ruleset creation as a permission grant, which is the correct boundary. Hosted verification is the pull request carrying this change, which must produce `ios-gate` and pass it.
- **Limits:** Required-check contexts must appear at least once before GitHub shows them as satisfiable; the first pull request after the ruleset is the proof. `review_ci.py` reads artifacts, not job names, so it is unaffected; the README now describes the `starter`-only pull-request lane.
