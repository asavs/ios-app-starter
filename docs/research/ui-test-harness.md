# UI test harness

Checked 2026-10-27. A: Apple and repository inspection; C: task description's reported UI quirks, not independently reproduced. Recommendation: propose an opt-in testing support module and a documented launch contract for generated apps.

The current `StarterApp/StarterAppUITests/StarterAppUITests.swift` sets individual launch argument defaults such as `-onboarding.completedVersion`, uses accessibility identifiers, and retains named screenshots. `docs/ci.md` explains attachment extraction. It does not establish a generic `-ui-testing` reset or SwiftData memory store. Apple documents a volatile argument defaults domain that takes precedence over app settings ([Apple, A](https://developer.apple.com/documentation/foundation/userdefaults/argumentdomain)). Overrides are not a reset of persisted defaults. A dedicated test launch flag should select an isolated suite and an in-memory container before app construction, use deterministic fixtures, and avoid deleting ordinary user data. Verify the flag cannot accidentally operate on a production store.

Keep identifiers as stable, nonlocalized strings. Sharing one Swift source file in app and UI-test targets avoids drift, but it must have target membership in both and no app-only dependencies; a small shared package is another option. Apple documents the accessibility identifier for UI automation ([WWDC25, A](https://developer.apple.com/videos/play/wwdc2025/344/)). Test real accessibility labels separately; identifiers are not labels. Inspect the actual accessibility tree before choosing queries: a reported Toggle identifier may attach to a row, and iPad confirmation dialogs can appear as popovers without a cancel button. These are reports to reproduce across supported OS/device layouts, not universal contracts. Exercise dismissal by tapping outside where supported, assert resulting state, and attach a screenshot of the main path. Test iOS 17 and current CI runtime; screenshots alone do not establish accessibility or feature correctness.

Apple recommends identifiers unique across the app, descriptive and stable as content changes; hidden accessibility parents can prevent discovery ([WWDC25, A](https://developer.apple.com/videos/play/wwdc2025/344/)). The Maestro project similarly recommends IDs while documenting wheel hierarchy caveats ([Maestro, B](https://docs.maestro.dev/get-started/supported-platform/ios/swiftui)); validate those observations with XCTest before adopting a workaround.

## Shared support contract

Propose a test-support product exposing a launch configuration and deterministic fixture hook, with an app-owned identifier source compiled into both targets. It must be opt-in and isolated from normal user data. Database supplies the in-memory factory; Settings accepts a test suite; neither requires the other. Demo a test that launches with isolated state, toggles a preference, sees a seeded item and attaches a screenshot. Test two launches for isolation and confirm a normal launch cannot enter the reset path. Accessibility identifiers support automation but do not substitute for VoiceOver labels.
