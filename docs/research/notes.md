# Notes tab: editor, drafts and Library references

Built as the Notes tab (2026-11-05, `ios-125.5`): `StarterApp/StarterApp/Notes`, see [modules.md](../modules.md#attachments) for what shipped. Research checked 2026-11-05 against the iOS 17 minimum, using `main` at `ff15a6f31e176bf97af73d29571d16240412e5fc`. This is a proposal for [slice 5](../design/feature-tabs.md), not evidence of a working Notes screen or iOS 17 runtime coverage. The ownership and migration decisions remain in [content ownership](content-ownership.md).

## Existing foundation

[StarterSchema.swift](../../StarterApp/StarterApp/Data/StarterSchema.swift) defines Note with a stable UUID, title, plain-text body, creation and modification dates in both the media V3 and text-only Text2 schemas. Media V3 also has ordered `NoteLibraryReference` rows keyed by note and Library item UUID. The text-only schema has no reference model. These are separate store histories; removing Attachments from a build does not establish that a previously created media store can open in the text-only build.

[ContentCoordinator](../../StarterApp/StarterApp/Data/ContentCoordinator.swift) exists only with Database and Attachments. Its `link` prevents a duplicate pair, `unlink` removes the reference, `items(for:)` returns a nil target for a missing item, and `deleteNote` deletes the note and its references without deleting Library items or files. These methods save the shared context and can throw; they do not themselves restore pending changes on failure. Library deletion removes references while preserving note text. The implementation must handle errors and context state explicitly, including a possible later save of failed pending changes.

[LibraryView](../../StarterApp/StarterApp/Library/LibraryView.swift) displays collected photos, files and links, uses a searchable field and distinguishes empty collection from no results. [LibrarySearch](../../StarterApp/StarterApp/Library/LibrarySearch.swift) trims whitespace and matches localized title, file name and link address in memory. Notes should follow the same search conventions while searching its own title and body. Library remains the place to collect and manage files and links; Notes owns authored text.

## Recommended interaction and persistence

Use a `NavigationStack` list ordered by `modifiedAt` descending, with a stable UUID tie-breaker. Provide Add, an empty state, a separate no-results state and a clearly labeled search field. Match trimmed title and body using localized case- and diacritic-insensitive matching, as Library does; preserve list order. For the starter's small local collections, in-memory filtering is a reasonable first implementation. Measure before promising performance for large bodies or libraries. Search must not silently include Library content.

Use a title field and a labeled multiline [TextEditor](https://developer.apple.com/documentation/swiftui/texteditor) bound to a value draft, not directly to the live model. Use [searchable](https://developer.apple.com/documentation/swiftui/view/searchable(text:placement:prompt:)) for filtering; verify its placement on each supported runtime. Apple's [search HIG](https://developer.apple.com/design/human-interface-guidelines/searching) describes search as a possible filter of the current view, and its [text views guidance](https://developer.apple.com/design/human-interface-guidelines/text-views) covers multiline editing. These APIs are available at the iOS 17 minimum; confirm actual behavior on that runtime. Avoid APIs introduced after iOS 17 as requirements.

Recommend explicit Save and Cancel for the first slice. A new blank draft creates no record until Save; Cancel discards it. An existing note opens as a copy of the saved values. Save inserts or updates only after the person acts, preserves `id` and `createdAt`, updates `modifiedAt` on a successful content change, and explicitly saves. Define a visible fallback title for an empty title without overwriting the saved body; permit body-only notes. Decide whether an entirely blank note can be saved before implementation.

Keep dirty draft state above the editor's presentation lifetime so switching tabs or a shell rebuild does not discard it. Intercept Back, tab hiding or another navigation away while dirty: offer Save, Discard and Keep Editing. A failed save keeps the draft and editor open, explains that changes are not saved, and offers retry or explicit discard. A canceled departure changes nothing. If the system terminates the process before Save, this in-memory draft is lost; do not promise recovery after termination. If product requires crash-resistant drafts, design durable draft storage and recovery separately, including privacy and reset behavior. Saved notes must survive termination and relaunch.

Use a dedicated editing context with autosave disabled, or another verified isolation strategy, so editing or a failed save cannot be committed by an unrelated shared-context save. On failure, preserve the value draft and discard or reset the failed transaction before retry; do not roll back unrelated changes. Apple's [save()](https://developer.apple.com/documentation/swiftdata/modelcontext/save()) throws, and [Build an app with SwiftData](https://developer.apple.com/videos/play/wwdc2023/10154/) describes autosave and explicit saves. Autosave alone does not provide the proposed visible success/failure boundary. Test the chosen strategy with real disk stores and independent contexts on iOS 17.

Delete asks for confirmation, then saves deletion before reporting success. With Attachments, use the coordinator's `deleteNote`; without it, delete the Note in a text-only path and save explicitly. On failure leave the note recoverable, display a retryable error, and prevent a subsequent unrelated save from committing the failed deletion. A shared-context coordinator currently needs a tested failure-isolation strategy; merely catching its error is insufficient.

## References in the editor

With Attachments compiled in, offer selection from existing Library items, identified by UUID. Save a new note before invoking the coordinator's reference operations, or implement a tested atomic transaction covering the draft and reference changes. Make the chosen sequencing and partial-failure behavior visible: a saved note must never be presented as if an unsaved reference succeeded. Avoid creating references to an unsaved or deleted target, and prevent duplicate pairs. Display references in their stored order; a missing target gets an unavailable state, never a guessed match by title. Fetch and save failures need visible retry or cancellation. The coordinator currently assigns `existing.count` as the next order, so removing a middle reference then linking another can duplicate order values; resolve and test deterministic ordering before relying on it.

Removing a reference or deleting a note leaves the Library item and original intact. Deleting a referenced item follows the existing Library confirmation and removes its references while retaining note text. Import, if offered from Notes, first collects through Library's existing ownership path and then links the saved item; failure at either step must clearly report what was saved. Prefer choosing an existing item for the first slice if this two-step recovery is not ready. When Attachments is absent, compile the full text workflow without the picker, references or coordinator; do not remove the Database dependency.

## Accessibility and verification before shipping

Use standard controls and meaningful labels for title, body, Add, Save, Cancel, search, delete and reference actions. A list row should announce its title or a localized untitled fallback and useful date without reading the entire body; expose deletion through an accessible action as well as touch. Keep the editor's text and error separately navigable, move focus to an error when appropriate, and restore a sensible focus after dismissal. Do not rely on color or placeholder text as the only label. Apple's [accessibility HIG](https://developer.apple.com/design/human-interface-guidelines/accessibility), [Dynamic Type session](https://developer.apple.com/videos/play/wwdc2024/10074/) and [SwiftUI accessibility session](https://developer.apple.com/videos/play/wwdc2024/10073/) inform this approach. Use semantic text styles, wrapping and layouts that remain usable at the largest accessibility sizes; verify keyboard and VoiceOver interactions on device.

Required evidence, not completed checks:

- Unit and disk-store tests for create, edit, unchanged save, dates, blank/title policy, localized title/body search, delete, and terminate/reopen. Inject save failures and verify retry, discard and later unrelated saves do not commit failed changes. Exercise switching tabs, navigation, hiding and shell reconstruction with a dirty draft, plus the documented termination boundary.
- With Attachments, test two notes linked to one item, duplicate selection, unlink, delete note, Library deletion/cancel, missing target, reordered references and failure at each save. Verify note text, item and original bytes as applicable after relaunch. With Database and no Attachments, build and test create/edit/search/delete and reopen; separately verify the existing incompatible-store recovery boundary. Do not infer cross-configuration migration support.
- Add XCUITests using stable accessibility identifiers for the main create/edit/search/delete and reference paths, save failure/retry, navigation choices and relaunch; attach screenshots. Run the pinned accessibility audit, manually exercise VoiceOver reading order and actions, largest Dynamic Type, contrast, touch targets and search. Cover empty and no-results states.
- Run the relevant scenarios on an actual iOS 17 simulator runtime and current supported runtimes, recording toolchain, OS and results. An iOS 27 pass alone is not iOS 17 coverage. Run the physical-phone UI and manual accessibility checks described by the team workflow.

## Open decisions

- Should entirely blank notes be allowed, and what localized fallback title should a body-only note display?
- Is losing an unsaved in-memory draft on process termination acceptable, or is durable draft recovery required?
- Should linking wait until the note is saved, and should Notes offer importing in the first release? Resolve partial success and reference ordering before implementation.
- Should deletion have undo or retention? That would change the lifetime of deleted records and may affect ownership cleanup.
