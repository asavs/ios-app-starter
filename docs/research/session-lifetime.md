# Timer session lifetime across tab changes

Checked 2026-11-02 against the iOS/iPadOS 17 minimum. Built as: pending. Research only; no runtime verification in this change. Apple documentation and WWDC are grade A evidence for API contracts. Repository findings below are source inspection; the proposed ownership and policies are recommendations.

Keep one session owner for the app process, created independently of whether Timer is visible. Hiding, reordering or reconstructing tabs must neither reset that owner nor stop its session. Persist enough state to reconstruct the same session after process death. A Live Activity is a presentation of the session, not its owner.

This extends [interval timing](interval-timing.md), [Live Activities](live-activities.md) and [screen-awake policy](screen-awake.md); those reports cover clock design, widget configuration and background execution options. The [feature-tab contract](../design/feature-tabs.md) landed in [PR #147](https://github.com/asavs/ios-app-starter/pull/147). Carry forward [PR #146](https://github.com/asavs/ios-app-starter/pull/146), inspected at `7aee161`, before implementing this recommendation; its toggle and restoration fixes solve existing bugs and remain required.

## Recommended ownership on iOS 17

Apple ties state storage to view identity: removal or a new identity ends that storage's lifetime ([Demystify SwiftUI, WWDC21](https://developer.apple.com/videos/play/wwdc2021/10022/), lifetime section). Ordinary `body` reevaluation with a stable identity does not itself reset state. Stable tab IDs help with reordering, but cannot preserve a removed destination's local state. Observation supports a shared model on iOS 17; `@State` owns it and environment or explicit references distribute it ([Managing model data](https://developer.apple.com/documentation/swiftui/managing-model-data-in-your-app), [Discover Observation, WWDC23](https://developer.apple.com/videos/play/wwdc2023/10149/), property wrappers section).

Introduce a host-owned, `@MainActor @Observable` session coordinator, or lift the session responsibilities out of `TimerScreenModel` into an equivalent service. Own one at the app composition root, above `WindowGroup` destinations, onboarding/database gates and the changing tab shell. Ensure early intent initialization and foreground scenes resolve the same instance, including when Timer has never been constructed. Inject defaults, paired time sources, cue output and the activity host for tests. Keep the modules optional under the existing `canImport` boundaries; a hidden runtime tab still has its compiled modules, while build-time removal must compile without the service.

The owner holds the run ID, immutable plan/times for that run, clock and current snapshot. Start, pause, resume, skip, reset, foreground reconciliation and intent commands all pass through it. Save the resulting record and enqueue the corresponding activity change from this owner, without requiring SwiftUI `onChange` or a mounted Timer screen. Use an owner-level transition callback or equivalent event delivery for phase/completion changes from `SessionTimer`; avoid adding another polling loop. Deduplicate by session and transition so two views cannot save, publish or play the same cue twice.

Keep plan sheets, preset selection sheets and navigation local to the screen. A rebuilt screen reads the owner's snapshot and sends commands; it does not load a fresh plan over a running or paused session. Keep the activity service's ordered queue from #146. Main-actor isolation alone does not make asynchronous calls execute as one transaction: validate session identity and current activity existence when the queued operation runs. Persist the synchronous command result before awaiting publication, and never write an old record back after that await.

On launch, load and validate the record before reconciling activities, even if another tab is selected. On foreground entry, sample current time, reconcile missed phase boundaries/completion and any intent changes, then publish once. During a live process, route intents through the same owner; retain record-based reconstruction for a cold intent launch. Preserve #146's foreground intent callback behavior without relying on a callback that a newly built screen can overwrite.

Tie sampling to app execution needs: the existing foreground cadence can initially remain while any scene is active, including a hidden Timer, so boundaries still reach the owner. Stop sampling when no scene is active without issuing a session pause, then derive the current snapshot on activation. This needs an explicit sampling lifecycle API; `SessionTimer` currently starts its refresher whenever its snapshot is running. A future slower hidden-screen cadence must still deliver phase/completion changes without requiring a visible observer.

## Time that survives a rebuilt screen or process

[`SessionClock`](../../Modules/SessionTimer/Sources/SessionClock.swift) uses `ContinuousClock.Instant`; Apple documents it as advancing during sleep with instants comparable only locally during program execution ([ContinuousClock](https://developer.apple.com/documentation/swift/continuousclock), [Meet Swift Async Algorithms, WWDC22](https://developer.apple.com/videos/play/wwdc2022/110355/), clocks section). It supports accurate elapsed time in a surviving owner, not a durable timestamp.

| State | Lifetime and representation |
| --- | --- |
| Continuous clock anchor, sampling task, view subscriptions | Process-local. Reuse across screen reconstruction; never serialize an instant as a cross-launch deadline. Cancel/restart sampling explicitly without pausing the logical run. |
| Session UUID, plan and configured times | Persist across launch. Keep the UUID through pause/resume/skip, tab changes and restoration. Allocate a new UUID only for a new run. |
| Banked active duration, has-started, running start `Date` | Persist using `SessionClockState`. Paused runs have no running date. Normalize finished state to full duration with no running date, as #146 does. |
| Phase date range, paused remaining, projected session end and stale date | Activity content derived from the authoritative snapshot and a matching wall-clock sample. Regenerate after pause/resume/skip/restoration; do not persist a competing activity clock. |
| Selected/visible tabs and screen-awake requests | Independent presentation state. A tab setting cannot clear the session record or change its clock. |

Capture continuous time and `Date` together for a command, derive one snapshot, persist its corresponding clock state and derive activity dates from that same snapshot/sample. [`SessionActivityState(snapshot:plan:now:)`](../../Modules/SessionActivity/Sources/SessionActivityState+Snapshot.swift) already does the projection: remaining time becomes a phase range and session-end date. Its running dates let [timer text](https://developer.apple.com/documentation/swiftui/text/init(timerinterval:pausetime:countsdown:showshours:)) count without app ticks.

Wall-clock changes need an explicit recovery policy. Current restoration adds `max(0, date - runningSince)` to banked time and clamps elapsed to plan duration; a stored future start effectively starts now. Recommend retaining monotonic elapsed time during a surviving process and rebasing exported activity dates after a significant wall-clock change. Across process death, use the persisted date fallback, disclose its clock-change limitation and test forward/backward changes. Time zone changes alter displayed local times, not absolute `Date` intervals. Exact recovery across a clock adjustment and process death is unresolved with this record alone.

## Consistency requirements

| Event | Required session, storage and activity behavior |
| --- | --- |
| Start / start again | Commit one new run ID and record. Request one activity if the app preference and system authorization allow it. Activity failure must not stop the timer. |
| Pause / resume from app or intent | Keep ID and plan; bank elapsed time or establish a new anchor, save, then publish paused remaining or new running ranges. All visible screens follow, including when no scene-phase change occurs. |
| Skip | Derive the next phase while preserving running/paused status; save and publish once. Skipping the final phase completes the session. |
| Completion / reset | Completion saves terminal state and ends with final content; reset clears the record and ends immediately. Preserve #146's 15-minute finished Lock Screen card policy. A retained final card must say Done, never show a running countdown. |
| Hide, reorder, switch or rebuild tabs | No start/stop/reset, record clear, new UUID or duplicate activity. Hidden sessions still process transitions while the app is executing. A reconstructed screen immediately shows the current phase/status. |
| App foreground / relaunch elsewhere | Restore without Timer, reconcile time and intents, end unrelated activities, update the matching activity or end it if completed. An absent/unreadable record requires orphan cleanup. |
| App Live Activity preference off / on | Off ends the activity immediately without pausing or clearing the session. On re-sends the current stored/owned session immediately, including mid-phase, as #146 fixes. Rapid off/on must resolve in order; no tick or phase wait. |
| System authorization or dismissal | Check system authorization separately from the app preference. Refused requests leave the session intact. Removing a Live Activity does not stop its underlying task; decide whether later transitions should recreate it. |

[Activity authorization](https://developer.apple.com/documentation/activitykit/activityauthorizationinfo) provides a synchronous enabled check and an authorization update sequence. [Activity request](https://developer.apple.com/documentation/activitykit/activity/request(attributes:content:pushtype:)) is normally foreground-only; a `LiveActivityIntent` is the documented exception. The foreground Settings toggle can request immediately, whereas generic background reattachment must tolerate refusal and retry at an eligible foreground reconciliation. Scope interaction to the iOS 17 APIs: [adding interactivity](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities) places `LiveActivityIntent` execution in the app process, not a particular view or scene.

[Meet ActivityKit, WWDC23](https://developer.apple.com/videos/play/wwdc2023/10184/), lifecycle section, covers activity states and launch reattachment; enumerate [current activities](https://developer.apple.com/documentation/activitykit/activity/activities) to reconcile them. [Update](https://developer.apple.com/documentation/activitykit/activity/update(_:)) cannot revive an ended activity. [End](https://developer.apple.com/documentation/activitykit/activity/end(_:dismissalpolicy:)) takes final content and a dismissal policy, so ended and removed are distinct states.

Keep the existing screen-awake intent: request it only when a running Timer is actually visible in an active scene. Release on hiding, leaving, pause, finish or scene inactivity, without changing the session. Reacquire on reappearance even when `isRunning` never changed; relying on the existing change observer alone risks leaving it off after a tab round trip. `UIApplication.isIdleTimerDisabled` is app-wide, so overlapping scenes need coordinated requests rather than competing true/false writes ([idle timer](https://developer.apple.com/documentation/uikit/uiapplication/isidletimerdisabled), [ScenePhase](https://developer.apple.com/documentation/swiftui/scenephase)).

## Failure cases and implementation verification

Use injected continuous and wall clocks and a recording activity host for deterministic checks. App-owner tests must run without constructing `StarterTimerView` or manually calling its `onChange` handler.

| Scenario | Required evidence |
| --- | --- |
| Remove Timer during a running phase, cross several boundaries, then restore it | Same owner/UUID/plan and correct elapsed time; one effect per observed transition, completion persisted and activity ended even while the screen is absent. Repeat paused, reordered, and with the whole shell reconstructed. |
| Relaunch with Home or Settings selected | Owner adopts running/paused/finished records before Timer appears; elapsed background time is included only for running state. Opening Timer agrees with the activity; Start again creates exactly one new run. |
| Activity still shows after logical completion | While app executes, assert final end exactly once with final state. After suspension, assert terminal reconciliation on next execution. Distinguish the intentional final card from an orphan active card. Test missing, malformed and unknown-plan records. |
| Preference off while the island is up, then on mid-phase | Activity count becomes zero then one after queued work drains; session ID and elapsed time continue. Repeat rapid toggles with a deliberately delayed host and with no Timer view. Preserve #146's regression tests. |
| Island intent with Timer visible, hidden, or process cold | One record mutation and activity publication; mounted screens agree immediately, without requiring scene activation. Stale session IDs and a finished session cannot restart the run. |
| Navigate away and back while running; background and reactivate | Fake idle setter confirms release/reacquire and no session stop. Two scenes cannot release another scene's active request. Verify actual screen dimming on a device. |
| Long run and clock changes | Controlled forward/backward dates, exact boundaries, paused-zero state, suspension beyond several phases and whole-session expiry; date projection and record round trips agree. No record writes or ActivityKit lookups on ordinary within-phase ticks. |

Add XCUITest paths with the shared launch harness, accessibility identifiers and screenshots: start, hide/reveal/reorder, pause/resume/skip, tab restoration after relaunch, and Settings off/on mid-session. An in-app activity count against a fake proves routing, not real Lock Screen rendering. Run targeted owner/module and UI tests locally on the available Mac simulator, then inspect hosted results. Verify iOS 17.0.1 separately through the compatibility lane and record named passing/skipped tests; iOS 27 results do not establish the minimum. Keep removed-module build coverage. On the phone, check the island/Lock Screen, intent authentication and cold launch, activity dismissal, and actual screen-awake behavior. These are future implementation acceptance checks, not evidence supplied by this research.

## Limits and unresolved decisions

An owner surviving navigation does not keep the process executing in the background. A Live Activity has no widget timeline; a [stale date](https://developer.apple.com/documentation/activitykit/activitycontent/staledate) marks outdated content rather than executing the next phase. With the current local-only design, phase labels and completion can remain stale while suspended until the app or intent runs again ([Displaying live data](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities), [Bring widgets to life, WWDC23](https://developer.apple.com/videos/play/wwdc2023/10028/)). Preserve the truthful stale presentation; do not promise phase-accurate background updates from this refactor. Background notifications/push choices remain in the existing research. AlarmKit or newer scheduling APIs cannot supply the iOS 17 baseline.

Before implementation, settle whether a manually dismissed activity should restart on the next session transition; current host absence cannot distinguish dismissal from a refused start. Also settle cue catch-up while Timer is hidden: recommend one current transition cue while foregrounded and no burst of historical sounds on restoration, with view-local haptics only where useful. Keep the existing finished-card retention unless product requirements change. The persisted-date clock-change limitation and multi-scene screen-awake aggregation require explicit tests; neither has runtime evidence from this report.
