# Pushing the timer's phases to its Live Activity

Built as: pending. Research only, written 2026-11-03 by claude-mac for board task `ios-bqq`, route 2 of `ios-0ik`. Source grades: A = Apple documentation or WWDC session; B = maintained third-party documentation or a developer report; C = forum post. Apple pages were read through their documentation JSON endpoints on 2026-11-03.

The timer's Live Activity shows one phase at a time. When a phase ends while the app is suspended, nothing in the app can publish the next one: the state goes stale, the system re-renders the view once at the stale date, and since [#151](https://github.com/asavs/ios-app-starter/pull/151) that render shows the next phase from a schedule carried in the state. A second boundary without the app still ends in "Phase over". [live-activities.md](live-activities.md) names the routes that remove the limit; this document works out the one Apple documents for a suspended app: a server that sends each phase to APNs at its time. The starter is getting a server anyway, for API keys ([`ios-s9.1`](../design/ai-adapters.md), backend-owned keys), so this route costs one more job on that server rather than a new piece of infrastructure.

## What Apple provides

A Live Activity started with `pushType: .token` gets a push token of its own, delivered asynchronously: "The `pushToken` isn't available immediately after calling `request(attributes:content:pushType:)`, because push token creation happens asynchronously and may take some time." The app observes `activity.pushTokenUpdates` with `for await`, which "makes sure you receive the first push token, and any updates to it", and sends each token to its server. Tokens change during an activity's life: "invalidate the previous, now-outdated token on your server when you receive an updated token" ([ActivityKit push notifications, A](https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications)). Only ActivityKit hands out these tokens: "you can't use the User Notifications framework to register your Live Activity for push notifications" (same page).

The server sends an HTTP/2 `POST` to `https://api.sandbox.push.apple.com/3/device/<token>` (development builds) or `https://api.push.apple.com/3/device/<token>` (production), with headers `apns-push-type: liveactivity`, `apns-topic: <bundle ID>.push-type.liveactivity`, `apns-priority: 5` or `10`, and a bearer `authorization` token ([Sending notification requests, A](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns); [ActivityKit push notifications, A]). The payload is an `aps` dictionary with `timestamp` ("the current time in seconds since 1970 to allow the system to always display the most recent ActivityKit push update"), `event` (`update` or `end`; an end "include[s] the final content state"), `content-state` matching the `ContentState` type with no custom encoding ("Custom encoding strategies will result in update failures"), and optional `stale-date`, `dismissal-date`, `alert` and `relevance-score`. The whole payload is limited to 4 KB (4096 bytes), uncompressed ([Sending notification requests, A]). The timer's state encodes under 1 KB today and under 4 KB with eight long upcoming phases (`SessionActivityTests`), so the schedule fits in a push as it fits in a local update.

Priority decides the budget. "The system allows for a certain budget of ActivityKit push notifications per hour." Priority 10, the default, "counts it toward the notification budget that the system imposes" and "If you exceed the budget, the system may throttle your ActivityKit push notifications." Priority 5 "doesn't count toward the budget" ([ActivityKit push notifications, A]); WWDC23 adds that low priority updates "are delivered opportunistically, which lowers the impact on the user's battery life", that "there is no limit on how many updates you can send" at that priority, and recommends it "for the majority of your Live Activity updates" ([WWDC23 10185, A](https://developer.apple.com/videos/play/wwdc2023/10185/)). No page states the budget's number. `NSSupportsLiveActivitiesFrequentUpdates` (iOS 16.2) raises it: "Set the corresponding value to `true` to enable your Live Activities to receive frequent updates with remote push notifications" ([Info.plist key, A](https://developer.apple.com/documentation/bundleresources/information-property-list/nssupportsliveactivitiesfrequentupdates)), and people can turn frequent pushes off in Settings; the app reads `ActivityAuthorizationInfo.frequentPushesEnabled`, sends it to the server, and watches `frequentPushEnablementUpdates`; WWDC23 warns that "if this value changes, the system will end all ongoing activities" ([WWDC23 10185, A]).

Push-to-start exists from iOS 17.2: `Activity.pushToStartTokenUpdates` is "an asynchronous sequence you use to observe changes to the token for starting a Live Activity with an ActivityKit push notification" (iOS 17.2+, [pushToStartTokenUpdates, A](https://developer.apple.com/documentation/activitykit/activity/pushtostarttokenupdates)); "you don't have to start a Live Activity from your app to receive the push-to-start token", the start payload needs `event: start`, `attributes-type`, `attributes` and an `alert`, and on iOS 18 `input-push-token: 1` asks for an update token in the same push ([ActivityKit push notifications, A]). On iOS 17.1 and earlier, pushes can update and end but not start ([same page]). The timer doesn't need it: the app starts the activity in the foreground when the session starts.

Responses: 200 with an empty body on success; otherwise JSON with a `reason`. The ones a timer server will meet: `BadDeviceToken` (400, "the token matches the environment": a sandbox token sent to production, or the reverse), `Unregistered` (410, the token "is inactive for the specified topic", with a `timestamp` in milliseconds; don't retry), `ExpiredProviderToken` and `InvalidProviderToken` (403), `TooManyProviderTokenUpdates` (429, the signing token refreshed more than once in 20 minutes), `PayloadTooLarge` (413), `TooManyRequests` (429, retry with delay), `InvalidPushType` (400) ([Handling responses, A](https://developer.apple.com/documentation/usernotifications/handling-notification-responses-from-apns)). APNs "stores only one notification per bundle ID" per device, so a device offline through several boundaries receives the last one, which is what the timer wants ([Sending notification requests, A]).

## What it asks of the account

Two changes, both for Asa to approve before anyone enables them, per AGENTS.md.

1. **The Push Notifications capability on the App ID.** "Enabling this option in iOS adds the `aps-environment` to the app", and "In your developer account, enable the push notification service for the App ID assigned to your project" ([Registering with APNs, A](https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns)). The entitlement's value follows the profile: "if you're using a development provisioning profile, Xcode sets the value to `development`. Production provisioning profile and [TestFlight] use `production`" ([aps-environment, A](https://developer.apple.com/documentation/bundleresources/entitlements/aps-environment)). Today the Live Activity needs no capability at all ([live-activities.md](live-activities.md)); this is the first entitlement the starter's App ID would carry beyond the defaults, and the development profile that `run-on-device` uses today is a wildcard one, which can't carry it: the first signed build after enabling the capability registers an explicit App ID and a new development profile (compare the journal entry of 2026-11-01 on the widget extension's signing).
2. **An APNs authentication token signing key.** Requested at developer.apple.com/account/resources/keys; Apple returns "a 10-character string with the Key ID" and "an authentication token signing key, specified as a text file (with a `.p8` file extension)", which "must remain private to prevent anyone else from generating those tokens". One key serves every app of the team ("You can use one token to distribute notifications for all or a subset of your company's apps"); team-scoped keys are limited to two per environment ([Token-based connection, A](https://developer.apple.com/documentation/usernotifications/establishing-a-token-based-connection-to-apns)). The key is a secret for GitHub Secrets and the server's secret store, never the repository, example files, logs or an app bundle (AGENTS.md). A compromised key is revoked in the same place it was created.

The server signs a JWT with `alg: ES256`, `kid` = the Key ID, `iss` = the Team ID and `iat` = now, refreshed "no more than once every 20 minutes and no less than once every 60 minutes" ([Token-based connection, A]). The connection is bound to one team and to the bundle IDs it first pushes to; a new bundle ID means new connections.

## What the server has to do

The server's job is small and time-driven: it knows a session's schedule and sends each phase when it begins.

- **Registration.** When a session starts, the app sends the activity's push token, the session identifier, the plan's phases with their absolute dates (the same `upcoming` schedule the state carries), the device's `aps-environment` (so the server picks the sandbox or production host) and `frequentPushesEnabled`. When `pushTokenUpdates` yields a new token the app sends it and the server drops the old one. Pause, resume, skip and reset send a new schedule or a cancellation; completion in the foreground sends an end so the server stops.
- **Sending.** At each boundary the server sends `event: update` with the `SessionActivityState` for the new phase (the same JSON the app encodes, with its `upcoming` trimmed to the phases after it), `timestamp` = now, `stale-date` = the phase's end, `apns-priority: 5`. At the session's end it sends `event: end` with the finished state and a `dismissal-date` fifteen minutes on, matching the app's dismissal policy. Priority 10 only if a phase boundary is late by more than a few seconds and the device is known to be awake; with the stale-render floor from #151 showing the next phase anyway, late delivery costs little, so the budget is never spent on routine boundaries.
- **Stopping.** A 410 `Unregistered` or a 400 `BadDeviceToken` ends the schedule for that token. A token the app never refreshed after the activity ended is harmless: APNs reports 410 and the server forgets it. Schedules expire with the session's end plus the dismissal window.
- **Offline device.** APNs keeps the last push; the device shows the newest phase when it reconnects. The state's `timestamp` keeps an older push that arrives late from overwriting a newer one.
- **Clock.** The server's clock drives delivery; the dates in the state are the device's dates from the moment the app published them. A few seconds of skew only shifts delivery; `Text(timerInterval:)` on the device counts from the dates in the state, not from arrival.

What the server stores per session is the token, the environment, the schedule and the next index: no personal data, no content beyond phase titles and kinds that the activity already shows.

## How it fits the app

`StarterSessionActivity` already owns the one activity and `SessionActivityController` already serialises every ActivityKit call, so the client side is contained:

- `ActivityKitHost.start` passes `pushType: .token` instead of `nil` when the server is configured, and the host exposes `pushTokenUpdates` for the activity it started. The controller, which already hears every session change, forwards the token and the schedule to a `SessionPushRegistrar` (a small client of the server) and tells it about pause, resume, skip, reset and end. Nothing changes for a build without a server: `pushType` stays `nil` and the registrar is absent, so the module keeps working as it does today.
- The app's own local updates continue in the foreground; the server covers the boundaries the app misses. Both carry a `timestamp`, so whichever arrives later wins, and the state is identical, so there's no flicker.
- The widget views need nothing: the content state is the same `SessionActivityState`, decoded from the push exactly as from a local update, which is why the state must keep plain `Codable` conformance with no custom strategy.
- A fake registrar and a recording host test the client side without APNs: token forwarded on start and on change, schedule re-sent on pause and resume, cancellation on reset, environment read from the entitlement. Delivery itself is tested from a Mac with `curl` against the sandbox host and a token logged by a debug build, as Apple describes, including on the simulator ("use a Mac with Apple T2 chip or a Mac with Apple silicon that runs macOS 13 or later"), and on the phone with the screen locked through two boundaries.

## Costs and limits

- Two account changes (capability, signing key) and a running server; the template default stays off this route until the server exists, as [live-activities.md](live-activities.md) says.
- Delivery is best effort at priority 5 and budgeted at priority 10; Apple states no number. A phase change a few seconds late is the expected case, which is why the stale-render floor stays.
- A device with no network for a whole session sees only the floor. Nothing here replaces the sounds at boundaries, which remain a Cues decision (local notifications or background audio, [background-audio.md](background-audio.md)).
- Pushes stop when the person turns frequent pushes off only in the sense of the budget; ordinary priority-5 updates keep flowing. Turning Live Activities off for the app ends the activity; the next token update never comes and the server sees 410.

## Open questions

- Whether the API-key server in `ios-s9.1` is the right home (one more scheduled job and one secret) or the pushes deserve a separate minimal service; the design of that server decides.
- Whether to send priority 10 for the final `end` so "Done" lands on time, spending one budgeted push per session.
- Whether the demo's identity (`com.asaschaeffer.starterappdemo`) or the template's gets the capability first; the template default `com.example.StarterApp` can never be registered, so the demo overlay is the only place to try it on a phone.
