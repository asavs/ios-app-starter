# Chat UI research

Checked 2026-10-31 by Codex. Research only; no Chat module or provider is implemented. Source grades: A = Apple documentation, HIG, WWDC or first-party code; B = an implementation or its maintainer's documentation; C = anecdote. A describes the contract, not proof of every OS behaviour. Recommendations below are design judgments, not tested code. Apple API availability comes from the documentation's Markdown metadata; links point to the readable pages. Repository revisions are recorded below because default branches can change.

## Recommendation

When an app needs chat and implementation is approved, build a small optional SwiftUI module with a chronological transcript, a growing composer, message selection and explicit sending/error states. Keep its iOS 17 minimum. Start with `ScrollView` and `LazyVStack`, stable message identifiers and a separate follow-latest policy. Give the app control over message content, attachment presentation and actions. Use Theme for semantic colors and text styles, without making the transcript depend on Database, an AI SDK or a messaging service. Follow the existing [module rules](../modules.md).

Treat the composer and transcript as separate components. A source supplies displayable messages; an app-owned controller connects that source to a provider. An ordinary conversation, a local model, a server stream and a future bridge can then share the UI. Transport and channel contracts remain future work in [roadmap milestones 11 to 13](../../roadmap.md#milestones).

Adopt no chat dependency yet. The three SwiftUI candidates below offer useful patterns, but bring either platform-specific infrastructure, media dependencies or an AI-oriented scrolling policy. Before choosing custom SwiftUI over a collection-view bridge, prototype pagination, streaming height changes and selection on iOS 17 and the current runtime. No library was built and no Messages screen was inspected on a simulator or phone during this research.

## 1. Messages conventions, composer and keyboard

Apple documents blue bubbles for iMessage and green bubbles for RCS/SMS/MMS. iMessage and RCS support typing indicators and delivery/read receipts. These colors describe a transport in Messages; a generic app should choose semantic outgoing/incoming colors without implying it uses iMessage ([message types, A](https://support.apple.com/en-us/104972)). Apple also documents swiping left on a message bubble to reveal conversation timestamps, tapping the text field to compose and using Send ([send and reply, A](https://support.apple.com/guide/iphone/send-and-reply-to-messages-iph82fb73ba3/ios)). Those guides describe the current OS, so they do not establish an exact iOS 17 layout.

Suggested defaults for an implementation:

| Element | Proposed behaviour | Evidence and limits |
| --- | --- | --- |
| Bubbles | Rounded, content-sized incoming and outgoing bubbles on opposite semantic sides; outgoing at trailing, incoming at leading. Mirror with layout direction. Use a readable neutral incoming surface and a tested outgoing tint. | Design choice inspired by Messages. This research found no public HIG specification for an exact radius, tail path or width percentage. |
| Consecutive messages | Group adjacent messages by the same sender within a configurable short time gap; use tighter spacing inside the group, and a tail, if used, only at its end. Break groups for day changes and system events. | Proposed grouping policy. A five-minute gap would be a product default, not an Apple rule. Keep sender identity available to accessibility even when its visible label is suppressed. |
| Time and receipts | Show a localized date/time separator at conversation boundaries and meaningful gaps. Make each message's time available through an accessible details action. Put delivery status under the relevant outgoing message, keeping failure and retry visible. | The swipe-to-reveal gesture is documented above. Exact separator thresholds and receipt placement are design choices. Show Delivered/Read only when the provider actually reports them; absence means unknown. |
| Composer | Leading Add attachment button, a labeled multiline text field, trailing Send button. Grow to a small line limit, then scroll inside the field. Preserve the draft when submission fails. Disable Send for an empty draft unless an attachment is ready. | A vertical `TextField` and closed-range `lineLimit` both exist in iOS 16, so fit iOS 17 ([field axis, A](https://developer.apple.com/documentation/swiftui/textfield/init(_:text:axis:)), [line range, A](https://developer.apple.com/documentation/swiftui/view/linelimit(_:)-4hzfa)). |

For example, a vertical field with `lineLimit(1...5)` can grow without measuring its text manually. The field becomes scrollable beyond the limit. At accessibility text sizes, use a height cap that still leaves useful transcript space and allow controls to rearrange. Keep Return available for line breaks in a multiline draft; decide keyboard shortcuts and Send behaviour explicitly. Changing the Return key's title alone does not define submission behaviour ([HIG virtual keyboards, A](https://developer.apple.com/design/human-interface-guidelines/virtual-keyboards)).

SwiftUI normally respects the keyboard safe area. Place the composer in a bottom safe-area inset; avoid an overlay that covers the last message, and avoid opting the transcript out with `ignoresSafeArea(.keyboard)`. Use `.scrollDismissesKeyboard(.interactively)` for drag dismissal. Test multiline growth, interactive dismissal, rotation, iPad floating keyboards and hardware keyboards. For a UIKit bridge, use the keyboard layout guide rather than a fixed keyboard height ([safe areas, iOS 14+, A](https://developer.apple.com/documentation/swiftui/view/ignoressafearea(_:edges:)), [bottom safeAreaInset, iOS 15+, A](https://developer.apple.com/documentation/swiftui/view/safeareainset(edge:alignment:spacing:content:)-4s51l), [keyboard dismissal, iOS 16+, A](https://developer.apple.com/documentation/swiftui/view/scrolldismisseskeyboard(_:)), [HIG virtual keyboards, A](https://developer.apple.com/design/human-interface-guidelines/virtual-keyboards)).

On iOS 26+, standard toolbars adopt Liquid Glass. For a custom bottom composer, use the **vertical-edge** `safeAreaBar(edge: .bottom)` overload, which reserves space and extends scroll edge effects; apply glass to the controls where appropriate. `safeAreaBar` does not itself promise a glass background. A custom `glassEffect` defaults to regular glass in a capsule. Keep bubbles in the content layer with ordinary fills. The HIG reserves glass for controls/navigation and advises restraint with custom toolbar backgrounds ([WWDC25: Build a SwiftUI app with the new design, A](https://developer.apple.com/videos/play/wwdc2025/323/), [vertical safeAreaBar, iOS 26+, A](https://developer.apple.com/documentation/swiftui/view/safeareabar(edge:alignment:spacing:content:)-9hwgb), [glassEffect, iOS 26+, A](https://developer.apple.com/documentation/swiftui/view/glasseffect(_:in:)), [HIG materials, A](https://developer.apple.com/design/human-interface-guidelines/materials), [HIG toolbars, A](https://developer.apple.com/design/human-interface-guidelines/toolbars)). On iOS 17 and 18 use `safeAreaInset` and a conventional surface/material. These are implementation recommendations, not a measured reproduction of the iOS 26 Messages composer.

## 2. Transcript layout, scrolling, performance and selection

Keep messages in chronological order, oldest first, with the initial viewport at the bottom. Avoid reversing the data or rotating the whole list as the initial solution: those approaches complicate reading order, gestures, alignment and accessibility. `List` offers native row infrastructure; `ScrollView` with a lazy stack offers direct bubble spacing and background control. Apple's anchor documentation gives a `ScrollView`/`LazyVStack` example. It does not establish equivalent chat behaviour for `List`; prototype it before choosing it.

| API or technique | Availability against iOS 17 | What it establishes |
| --- | --- | --- |
| `defaultScrollAnchor(.bottom)` | iOS 17+ | Sets an initial/content-size-change preference. Apple says the user may scroll away and the view may consult the anchor when size changes. It is not a complete follow-latest policy ([A](https://developer.apple.com/documentation/swiftui/view/defaultscrollanchor(_:))). |
| `scrollPosition(id:anchor:)` with `scrollTargetLayout()` | iOS 17+ | Binds position to stable row identity; SwiftUI attempts to keep that row visible when layout/data change. `.bottom` prefers bottom alignment ([A](https://developer.apple.com/documentation/swiftui/view/scrollposition(id:anchor:))). |
| `defaultScrollAnchor(_:for:)` | iOS 18+, needs a fallback | Separates initial offset, size changes and alignment for content smaller than the viewport. Apple's example combines bottom default with top-leading short-content alignment ([A](https://developer.apple.com/documentation/swiftui/view/defaultscrollanchor(_:for:))). |
| `ScrollPosition` and `scrollPosition(_:anchor:)` | iOS 18+, needs a fallback | Adds explicit edge/point positioning. Apple distinguishes keeping an edge stable from preserving an exact point offset ([A](https://developer.apple.com/documentation/swiftui/view/scrollposition(_:anchor:))). |
| `onScrollGeometryChange` | iOS 18+, needs a fallback | Derive a small value such as `isNearBottom`; avoid invalidating the transcript for every pixel ([A](https://developer.apple.com/documentation/swiftui/view/onscrollgeometrychange(for:of:action:))). |

Implement follow-latest as state independent of the anchor. Initial load and the person's own Send can move to the latest message. Incoming messages, a typing row and streaming growth follow only while the person is already near the bottom. When they read history, preserve their position and show a New messages button. Explicitly tapping that button resumes following. On iOS 17, use a bottom marker and a named-coordinate-space geometry/preference measurement for proximity; marker appearance alone does not measure the distance. On iOS 18+, derive the proximity Boolean through scroll geometry. The roughly 100-point threshold in MessagingUI is an example to tune, not a system standard ([TiledScrollPosition source, B](https://github.com/FluidGroup/swiftui-messaging-ui/blob/1ec611adfb17c74075239565273f6902cdf77db6/Sources/MessagingUI/Tiled/TiledScrollPosition.swift)).

Preserve the first visible message ID and its visual position when prepending history. Stable identity alone is not proof that pixel offsets survive variable-height insertions. Schedule a scroll request after the target exists, and exercise a single long streaming row whose ID stays unchanged while its height grows. Image loads, Dynamic Type, composer growth and keyboard transitions also change heights. Coalesce updates and avoid an animated scroll per token. Reproduce any jumps before adopting an inverted list or UIKit workaround.

For thousands of messages, page history and keep a bounded loaded window. Lazy stacks create visible content on demand; eager stacks construct their whole hierarchy. Apple recommends measuring on a device to decide whether laziness helps ([performant scrollable stacks, A](https://developer.apple.com/documentation/swiftui/creating-performant-scrollable-stacks)). `List` still gathers identifiers eagerly, although it creates rows on demand; make identity cheap and each `ForEach` element produce a constant number of top-level rows ([WWDC23: Demystify SwiftUI performance, A](https://developer.apple.com/videos/play/wwdc2023/10160/)). Keep IDs stable across streaming and server acknowledgement. Parse Markdown outside `body`, cache by message ID plus content revision, downsample attachments and measure scrolling, memory and updates on representative hardware. No universal List-versus-LazyVStack performance winner or measured message-count limit was established here.

Selection needs an explicit product decision. `.textSelection(.enabled)` is available from iOS 15, but on iOS 17 through 26 its menu acts on the entire `Text`. Apple's current documentation says range handles arrive in iOS 27 ([textSelection, A](https://developer.apple.com/documentation/swiftui/view/textselection(_:))). Whole-message Copy is a reasonable first version; do not advertise word/range selection on iOS 17 with that modifier. If range selection is required there, prototype a noneditable, selectable `UITextView` inside `UIViewRepresentable`, with inner scrolling disabled, correct size fitting and Dynamic Type. Verify links, long press, context menus and selection during streaming; avoid replacing text storage in a way that destroys an active selection. UIKit's text view is not a native AppKit implementation; a Mac path needs its own adaptation ([UITextView, A](https://developer.apple.com/documentation/uikit/uitextview)).

## 3. Streaming, typing, Markdown and link previews

Keep one stable message while its body grows. Distinguish waiting for a reply, remote typing, generating text, completion, cancellation and failure. A human typing event should expire if no refresh arrives; a disconnected provider must not leave dots forever. A model should be identified as AI and can say Generating response. Show a Stop control where generation can be cancelled, preserve useful partial text and expose retry after failure. The HIG asks for clear AI identification, understandable progress feedback and user control ([HIG generative AI, A](https://developer.apple.com/design/human-interface-guidelines/generative-ai), [HIG loading, A](https://developer.apple.com/design/human-interface-guidelines/loading)). These are UI policies available on iOS 17; a particular local model may require a newer OS/device.

Normalize provider updates to cumulative body snapshots with message ID and monotonically increasing revision. Apple's Foundation Models stream is already an async sequence of partially generated snapshots, available in iOS 26, so appending every snapshot as if it were a token delta would duplicate text ([ResponseStream, A](https://developer.apple.com/documentation/foundationmodels/languagemodelsession/responsestream)). A server delta adapter accumulates its deltas before publishing the same form. Foundation Models must remain an optional adapter with runtime/model availability checks; iOS 17 can use a fake, a compatible local engine or a server. Provider switching must not silently send an existing private transcript elsewhere.

Coalesce transient text snapshots at a measured cadence. A bounded latest-value stream is suitable for a complete replaceable snapshot; it is unsuitable for arbitrary insert/delete/receipt events, which must not be dropped. Durable updates need ordered reduction and resynchronization after a gap. Connect cancellation to the producer and network/model request, finish streams on every terminal path and cancel owned UI tasks on teardown. Cancelling observation alone does not retract an accepted outbound message. These are proposed adapter requirements to verify during implementation ([Swift AsyncStream documentation, A](https://developer.apple.com/documentation/swift/asyncstream), [Task cancellation, A](https://developer.apple.com/documentation/swift/task/cancel())).

For Markdown, store the original body string plus an explicit plain-text/Markdown format. A view-specific `AttributedString` cache should not become the transport or persistence format. Plain user text must not acquire formatting just because it contains asterisks. For trusted formatting intent, Foundation's inline parsing with whitespace preservation and SwiftUI `Text` can handle inline emphasis and links on iOS 17. Parsing a full Markdown document into attributes does not make `Text` a block renderer: Apple lists lists, blockquotes, code blocks and tables as unsupported ([Text Markdown limits, A](https://developer.apple.com/documentation/swiftui/text/init(_:tablename:bundle:comment:)), [interpreted syntax, iOS 15+, A](https://developer.apple.com/documentation/foundation/attributedstring/markdownparsingoptions/interpretedsyntax-swift.enum)).

| Renderer | iOS 17 fit | Tradeoff |
| --- | --- | --- |
| SwiftUI `Text` plus parsed inline attributes | Yes | Small dependency footprint; use a separate full-message Copy action. Block Markdown needs another renderer. |
| [MarkdownUI, B](https://github.com/gonzalezreal/swift-markdown-ui) | iOS 15+, macOS 12+ | Block rendering; upstream states it is in maintenance mode and points to Textual. Review unfinished syntax, selection and streaming cost before adoption. |
| [Textual manifest, B](https://github.com/gonzalezreal/textual/blob/main/Package.swift) | No: iOS 18+, macOS 15+ | Raising the app minimum or isolating an optional newer-OS product is a separate decision. An availability check in a view does not resolve an incompatible package deployment floor. |
| [MarkdownView, B](https://github.com/Lakr233/MarkdownView) | Declares iOS 16+, macOS 13+ | Explicit streaming support, throttling and incomplete-syntax handling; maintainer says it trades CommonMark completeness for presentation. Adds Litext, math, cmark and cache/collection dependencies ([manifest](https://github.com/Lakr233/MarkdownView/blob/main/Package.swift)). Benchmark and audit the resolved dependency graph first. |

During a stream, incomplete Markdown can change interpretation as delimiters close. Start with readable plain/inline output, or use a renderer with deliberate incomplete-syntax behaviour. Keep the raw text for Copy, preserve selection, and do not allow untrusted HTML or remote image loading merely because a renderer supports it. Link handling belongs to the app's URL-opening policy.

LinkPresentation works on iOS 17 (`LPMetadataProvider` and `LPLinkView` date to iOS 13). Fetch metadata asynchronously, with timeout, cancellation and caching; retain a plain tappable URL on failure. Size previews predictably so their arrival does not unexpectedly move the reader. `LPLinkView` has intrinsic sizing and needs a platform-view wrapper in SwiftUI ([metadata provider, A](https://developer.apple.com/documentation/linkpresentation/lpmetadataprovider), [link view, A](https://developer.apple.com/documentation/linkpresentation/lplinkview)). Fetching a preview contacts a URL outside the conversation; make automatic fetching a deliberate app policy. The companion attachments research is being prepared as `docs/research/attachments.md`; picker, file ownership, thumbnail and preview policy should be reconciled there before implementation. That report was not available on `main` when this one was written.

## 4. Accessibility

VoiceOver should traverse history chronologically and reach the composer after the transcript. Keep sender identity independent of left/right position or color. A plain bubble can combine sender, body, localized time and delivery state into one readable element; avoid reading a decorative avatar or repeated sender label twice. A suitable reading might be “Alex, Hello, 10:42 AM, received.” For a bubble containing actionable attachments or links, preserve those child actions rather than flattening them into an inert label. Offer Copy, Retry and message details through accessible controls/actions; timestamps must not depend solely on the horizontal reveal gesture ([HIG VoiceOver, A](https://developer.apple.com/design/human-interface-guidelines/voiceover), [accessibilityElement, iOS 13+, A](https://developer.apple.com/documentation/swiftui/view/accessibilityelement(children:))).

Use system text styles and allow multiline content to grow. Avoid fixed bubble heights and truncation; relax width constraints at accessibility sizes and reflow the composer controls. Test the longest sender name, localized dates, right-to-left content, links, attachment descriptions and all Dynamic Type sizes ([HIG typography, A](https://developer.apple.com/design/human-interface-guidelines/typography)). Use semantic colors, test outgoing text against its fill in both appearances and Increase Contrast, and keep sender/status cues beyond color. Use the starter's 44-point touch targets for attachment, Send, Stop and Retry controls ([HIG accessibility, A](https://developer.apple.com/design/human-interface-guidelines/accessibility)).

Do not announce every generated token or move accessibility focus for each arrival. Preserve the reader's focus; expose a stable generating state, then announce completion or a new-message count where useful. `AccessibilityNotification` is available on iOS 17, but the implementation must choose announcements sparingly and verify them with VoiceOver ([notifications, A](https://developer.apple.com/documentation/accessibility/accessibilitynotification)). When Reduce Motion is enabled, replace bouncing/pulsing typing dots with static dots or a status label, and suppress automatic decorative insert/scroll motion. `accessibilityReduceMotion` is available on iOS 13 ([environment value, A](https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilityreducemotion), [HIG accessibility, A](https://developer.apple.com/design/human-interface-guidelines/accessibility)). Stop offscreen indicator animations in either mode.

### Why a library can block another platform

SwiftUI in a package's public API does not guarantee portable internals. Unconditional UIKit views, platform-specific APIs and binary targets lacking a destination slice can fail a native macOS build. Exyte's Giphy dependency is a concrete example: its pinned [package manifest](https://github.com/Giphy/giphy-ios-sdk/blob/2.2.16/Package.swift) includes an XCFramework binary, whose [Info.plist](https://github.com/Giphy/giphy-ios-sdk/blob/2.2.16/GiphyUISDK.xcframework/Info.plist) lists iOS device, iOS simulator and Mac Catalyst slices, with no native macOS slice. Catalyst is distinct from native macOS. This establishes a blocker in the reviewed dependency graph; it does not diagnose the exact failure in a previously surveyed app without that app's revision and build log.

The `platforms` array sets deployment minimums; omitting macOS is not itself an exclusion list. SwiftPM supplies defaults for unspecified platforms and checks dependency floors against the consumer ([PackageDescription SupportedPlatform, A](https://docs.swift.org/package-manager/PackageDescription/PackageDescription.html#supportedplatform)). Conversely, adding `.macOS(...)` cannot supply missing source APIs or a binary slice. Future packaging should keep transport values portable, isolate UIKit/AppKit implementations, condition platform-specific target dependencies, and build each promised destination. `#if canImport` around a view alone does not fix an unconditional binary dependency. No optional platform is newly supported by this research.

## 6. Candidate API and provider boundary

Keep `ChatMessage` a value with `Identifiable`, `Sendable` and `Codable` fields. Suggested contents: stable message/conversation IDs, sender ID plus display name and human/assistant/system identity, an ordering key, optional creation/server timestamps, original body string with an explicit format, attachment references, content revision, generation state and delivery state. Keep local identity stable when a server ID arrives; model that mapping separately. Represent pending, accepted, delivered, read, failed and unknown distinctly, with receipts only where the provider supports them. Attachment references contain IDs and display metadata, not image buffers, temporary picker URLs or credentials. The app owns persistence and migrations, following [Database's boundary](database.md).

An illustrative contract follows. It is intentionally incomplete Swift, not a compiled package API; named page, capability, event and identifier types still need definition. Separate these declarations into files during implementation.

```swift
@MainActor
protocol ChatMessageSource: AnyObject, Observable {
    var messages: [ChatMessage] { get }
    var activity: ChatActivity { get }
    var capabilities: ChatCapabilities { get }
    var hasEarlierMessages: Bool { get }
    func loadEarlier() async throws
}

protocol ChatProvider: Sendable {
    func submit(_ request: ChatSubmission) async throws -> ChatAcceptance
    func events(in conversation: ConversationID, after: EventCursor?)
        async throws -> AsyncThrowingStream<ChatEvent, Error>
    func cancelGeneration(_ request: RequestID) async throws
}

// ChatView<Source: ChatMessageSource>(source: source, actions: actions)
// ChatComposer(draft: $draft, capabilities: source.capabilities,
//              onSend: controller.send, onAttach: app.chooseAttachment)
```

The observable source presents the currently loaded window; it does not expose provider SDK objects. An app-owned `@MainActor` controller/store implements it, reduces provider events, owns pagination and drafts, and supplies UI action closures. The UI observes that source and calls actions without knowing which provider is installed. Keep row rendering, grouping and follow-latest policy independent of the source so they can be tested with values. The protocol is a proposed substitution point for persisted, in-memory and test sources; keep the first concrete implementation small.

Provider events could include upserted message snapshots, removals, receipts, transient typing and generation completion. Define ordering, cursor recovery, acknowledgement reconciliation and deduplication before implementation. Subscribe/replay from a known cursor around submission so a fast reply cannot fall between Send and observation. Reconcile an outbound echo with the optimistic message's client ID instead of adding a duplicate. Retry with an idempotency key and keep failed drafts/content recoverable. These are requirements for later channel design, not claims that an iMessage bridge can currently provide every event or receipt.

| Adapter | What it supplies | What stays outside the UI |
| --- | --- | --- |
| In-memory fake | Deterministic messages, pagination, errors, receipts and scripted cumulative snapshots | Network, credentials and real model availability. Use it for previews and UI tests on iOS 17. |
| Local model | Availability/capabilities and generated snapshots; wraps Foundation Models only on supported OS/hardware | Model session, context limits and cancellation details. A generated answer does not imply a remote delivery/read receipt. |
| Server | Authenticated submission, stream decoding, reconnect/replay and normalized events | Shared provider credentials remain on the backend, per the roadmap. The UI gets safe user-facing failure state. |
| Future iMessage bridge | Channel IDs mapped to conversation/message IDs, actual receipt capabilities and outbound-echo reconciliation | Mac bridge deployment, identity mapping and transport. The optional live bridge requires the persistent Mac described in the roadmap. |

Keep the provider connection's lifetime with the controller/session. A disappearing view can cancel observation without cancelling an already accepted send. A Stop action targets a generation request; hide it or explain its capability when the provider cannot stop that work. The source should survive navigation if the conversation needs continuity. Clearing chat history and erasing app data must be explicit app operations, not effects of swapping providers or dismissing a view.

## Evidence required before implementation ships

Implementation remains pending an app need and approval. First compare the SwiftUI transcript with a collection-view prototype using the same fake and a large paginated dataset. Measure repeated prepend, append, streaming, attachment sizing, memory and selection on real hardware. Verify iOS 17 separately from iOS 27; a new SDK or a passing iOS 27 lane does not prove minimum-runtime behaviour.

The future module needs tests for grouping/day boundaries, stable IDs, duplicate echoes, stale revisions, cancellation, reconnection and send failure. Its app UI test should use stable accessibility identifiers such as `chat.transcript`, `chat.message.<id>`, `chat.composer`, `chat.send`, `chat.attach` and `chat.latest`; send a draft, receive a scripted reply, reveal older history without being pulled down, and attach a screenshot. Manual verification must cover VoiceOver focus/order, range selection where promised, Dynamic Type, contrast, Reduce Motion and keyboard variants. Review attachment ownership with the companion research and provider contracts with the later AI/channel designs before turning this sketch into a public API.
