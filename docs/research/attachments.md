# Attachments: photos, camera, files, preview and link previews

Built as: pending (`ios-6dd.6`). Checked 2026-10-31 by claude-mac-2 for board tasks ios-6dd.5 (this research) and ios-6dd.6 (the implementation). Source grades: A = Apple documentation, HIG, WWDC session or first-party sample; B = maintained implementation, Apple engineer forum reply or practitioner experiment; C = anecdote or search snippet. A describes the contract, not proof of every OS behaviour. Recommendations are design judgments, not tested code. Apple pages were read through their `developer.apple.com/tutorials/data/<path>.json` and `developer.apple.com/documentation/<path>.md` endpoints; links point at the readable pages. Every API below is available on iOS 17 unless a later version is named.

The app survey (`ios-6dd`) counted two apps that built all of this by hand: a photos picker and a document picker, camera capture through a UIKit representable, a Quick Look preview and a link preview, each wired to its own storage. The patterns are what the module takes; nothing is copied from those apps.

## Recommendation

Build an `Attachments` module around one fact: since iOS 16 every picker here is a system view that runs in another process, so the app needs no permission to let a person choose a photo or a file, and the only permission in the whole feature is the camera's. The module ships four pieces. `Attachment` is a value that names a stored file (its identifier, kind, display name, content type, size and the moment it was added) or a link with cached metadata. `AttachmentPicker` is a menu with Photos, Camera, Files and Link entries that presents `PhotosPicker`, a camera sheet, `fileImporter` or a paste field and hands back `Attachment` values once the files are copied. `AttachmentPreview` opens a stored file in Quick Look, shares it with `ShareLink` and draws a link with `LPLinkView`. `AttachmentStore` owns the files: originals under Application Support, thumbnails under Caches, a cache of link metadata beside them, and a sweep that removes files no record names any more.

Three decisions follow from the sources. First, the database keeps a reference, not the bytes: SwiftData's `.externalStorage` loads the whole blob with the record on iOS 18, and Apple's own engineer says to model large data as a separate relationship, so a file on disk named by the record is the simpler store, and it also gives Quick Look and the share sheet the URL they need. Second, the module never asks for Photos library access: `PhotosPicker` without a `photoLibrary` argument needs no usage string, and the one thing that argument buys, the asset identifier, is nothing a template attachment needs. Third, link metadata is fetched from the person's device, which tells the linked site their address, so the fetch runs only when a person adds a link, never on scroll, and the result is cached so it runs once.

What stays with the app: the SwiftData `@Model` that owns `Attachment` values and whatever it attaches to (the Database decision keeps every model in the app's schema), captions, upload or sync, a custom camera, video beyond pass-through, and where link previews appear.

## Photos

`PhotosPicker` (PhotosUI, iOS 16) is "a view that displays a Photos picker for choosing assets from the photo library", with single and multiple selection, a `PHPickerFilter` (`matching: .images`, `.any(of: [.images, .not(.screenshots)])`), `maxSelectionCount` and a `selectionBehavior` of `.default`, `.ordered`, `.continuous` or `.continuousAndOrdered` ([PhotosPicker, A](https://developer.apple.com/documentation/photosui/photospicker); [PhotosPickerSelectionBehavior, A](https://developer.apple.com/documentation/photosui/photospickerselectionbehavior)). On iOS 17 `.photosPickerStyle(.inline)` or `.compact` embeds it, `.photosPickerAccessoryVisibility` hides the bars around it and `.photosPickerDisabledCapabilities` turns off search or selection actions ([photosPickerStyle, A](https://developer.apple.com/documentation/swiftui/view/photospickerstyle(_:)); [WWDC23 10107, A](https://developer.apple.com/videos/play/wwdc2023/10107/)). The template uses the presented style: a sheet from a menu entry is what Mail, Notes and Messages do.

Privacy is the reason to use it. "The picker runs out of process, so your app doesn't need to request any library access to use it" ([WWDC22 10023, A](https://developer.apple.com/videos/play/wwdc2022/10023/)). "Your app can't access the picker directly and not even take screenshots of the picker content. Only what the user actually selected is passed back to your app" ([WWDC23 10107, A](https://developer.apple.com/videos/play/wwdc2023/10107/)). The limited-library setting does not touch it: "the picker will still show the entire photos library and all photos and videos can be selected by the user", and "no matter what user selects in the picker, PHAssets you can access will not change" ([WWDC20 10652, A](https://developer.apple.com/videos/play/wwdc2020/10652/)). Apple's instruction is direct: "please don't prompt for photo library access before showing the picker and don't require the user to grant you access before showing the picker" (same session). The photo-library half of `UIImagePickerController` is deprecated in favour of the picker; its camera half is not ([UIImagePickerController, A](https://developer.apple.com/documentation/uikit/uiimagepickercontroller)).

`NSPhotoLibraryUsageDescription` "is required if your app uses APIs that have read or write access to the user's photo library", and "attempting to access the Photos library without a valid usage description causes your app to crash" ([NSPhotoLibraryUsageDescription, A](https://developer.apple.com/documentation/bundleresources/information-property-list/nsphotolibraryusagedescription); [Delivering an enhanced privacy experience, A](https://developer.apple.com/documentation/photokit/delivering-an-enhanced-privacy-experience-in-your-photos-app)). The picker is not such an API. The string becomes necessary the moment the app touches `PHPhotoLibrary`: fetching assets, saving a captured photo back to the library (`PHAssetCreationRequest` needs read-write; `UISaveVideoAtPathToSavedPhotosAlbum` needs only `NSPhotoLibraryAddUsageDescription`) ([Requesting authorization to capture and save media, A](https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media)), or building the picker with `photoLibrary: .shared()`, which is the only way `PhotosPickerItem.itemIdentifier` is non-nil: "This value is nil if you create a Photos picker without a photo library" ([itemIdentifier, A](https://developer.apple.com/documentation/photosui/photospickeritem/itemidentifier)). The template does none of these. A captured photo goes into the attachment store, not the camera roll, so the module needs no Photos string at all; an app that wants "Save to Photos" adds the add-only string itself.

Loading is the part the surveyed apps got wrong. "The selection results you get are placeholder objects. A PhotosPickerItem conforms to Transferable, and allows you to load a representation you request", and "Image supports only PNG and JPEG file types through its Transferable conformance. To support other image types, create a custom Transferable model" ([PhotosPickerItem, A](https://developer.apple.com/documentation/photosui/photospickeritem)). An Apple DTS engineer explained the failure that follows: `Image.transferRepresentation` "only supports a contentType of public.png, which means loadTransferable(type: Image.self) will only return a non-nil success value if the PhotosPickerItem's supportedContentTypes also contains public.png. That is not always the case, often times the supportedContentTypes contains jpeg or heic instead", and recommended loading `Data` ([forum 709764, B](https://developer.apple.com/forums/thread/709764)). The WWDC22 session goes one better for large items: "To reduce memory usage, you can use FileTransferRepresentation to load selected assets as files. When loading assets as files, keep in mind that your app is responsible for managing their lifecycles. Files should always be copied to your app directory when received and deleted when they are no longer needed" ([WWDC22 10023, A](https://developer.apple.com/videos/play/wwdc2022/10023/)). `FileRepresentation`'s own example copies `received.file` inside the importing closure ([FileRepresentation, A](https://developer.apple.com/documentation/coretransferable/filerepresentation)). The module therefore defines a private `ImportedFile: Transferable` with a `FileRepresentation(importedContentType: .image)` (and `.movie` when the host allows video) whose importer copies the file straight into the store, so a 12 MB HEIC never sits in memory as `Data`, and `supportedContentTypes` (iOS 16) decides the kind before loading ([supportedContentTypes, A](https://developer.apple.com/documentation/photosui/photospickeritem/supportedcontenttypes)). Loading can fail "if the picker tries to download data from iCloud Photos without a network connection", so each selected item shows its own progress and failure, not one blocking spinner ([PhotosPicker, A](https://developer.apple.com/documentation/photosui/photospicker); WWDC22 10023).

## Camera

There is no SwiftUI camera. The two routes are `UIImagePickerController` with `sourceType = .camera`, which "provides a user interface for taking a new picture or movie (on devices that support media capture)", and AVFoundation for "fully customized image or movie capture" ([UIImagePickerController, A](https://developer.apple.com/documentation/uikit/uiimagepickercontroller)). The picker is portrait-only, "intended to be used as-is and doesn't support subclassing", presents full screen on iPhone (and Apple "recommends that you present the camera interface only full screen" on iPad), and must be checked with `isSourceTypeAvailable(.camera)` first (same page). The simulator has no camera, so that check is false there and the menu hides Camera. A template wants the simple capture sheet: a `UIViewControllerRepresentable` around the picker with `mediaTypes` set to still images, `allowsEditing` off, returning the `UIImage` from `didFinishPickingMediaWithInfo` for the store to encode. Live Photos arrive as a still unless `kUTTypeLivePhoto` is also requested, which the template does not. AVFoundation stays app code for the apps that need a viewfinder of their own.

The camera is the one permission. "In iOS and macOS 10.14 and later, the user must explicitly grant permission for each app to access the camera and microphone"; "if your app uses device cameras, include the NSCameraUsageDescription key in your app's Info.plist file"; without it "the system terminates your app" ([Requesting authorization to capture and save media, A](https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media); [NSCameraUsageDescription, A](https://developer.apple.com/documentation/bundleresources/information-property-list/nscamerausagedescription)). The string goes in `project.yml` under the app target's `info.properties`, beside `NSSupportsLiveActivities`, as an active sentence ("Take a photo to attach it to this note."); the module's README documents it, and `scripts/check-configuration.py` can fail a build that enables the module without the key. `UIImagePickerController` prompts on first presentation by itself. Apple's timing advice: "if photo or video capture isn't the main focus of your app, check for permission only when the user invokes your app's camera-related features" (same AVFoundation page), which matches the HIG's rule that onboarding carries a permission request only when the app cannot work without it ([onboarding.md](onboarding.md)).

So the module ships `CameraPermission: PermissionRequesting`, a requester that reads `AVCaptureDevice.authorizationStatus(for: .video)` and calls `requestAccess(for: .video)` when it is `.notDetermined`, mapping to `.granted`, `.denied` or `.unavailable`. An app whose feature is the camera puts `.permission(PermissionPrimer(... requester: CameraPermission()))` into its onboarding steps, exactly as `NotificationPermission` is used today, and gets the HIG primer with its single Continue button; `PermissionOverride.resolve(real:)` already swaps in a `FakePermission` for simulator tests ([modules.md](../modules.md#onboarding)). The template's demo does not put the camera in onboarding; it asks at the first tap on Camera, and when the status is `.denied` the menu entry opens an explanation with a link to Settings instead of a dead picker.

## Files

`fileImporter(isPresented:allowedContentTypes:allowsMultipleSelection:onCompletion:)` (iOS 14) "presents a system dialog for allowing the user to import multiple files"; iOS 17 adds the `onCancellation:` form ([fileImporter, A](https://developer.apple.com/documentation/swiftui/view/fileimporter(ispresented:allowedcontenttypes:allowsmultipleselection:oncompletion:)); [with onCancellation, A](https://developer.apple.com/documentation/swiftui/view/fileimporter(ispresented:allowedcontenttypes:allowsmultipleselection:oncompletion:oncancellation:))). The returned URLs are the trap: "This dialog provides security-scoped URLs. Call the startAccessingSecurityScopedResource method to access or bookmark the URLs, and the stopAccessingSecurityScopedResource method to release the access" (same page). "You must balance each call ... When you make the last balanced call to stopAccessingSecurityScopedResource(), you immediately lose access", and "if you fail to relinquish your access ... your app leaks kernel resources" ([startAccessingSecurityScopedResource, A](https://developer.apple.com/documentation/foundation/url/startaccessingsecurityscopedresource())). The module's rule: start access, copy the file into the store, stop access in a `defer`, and never keep the picked URL or a bookmark. A copy is what an attachment is; an app that wants to edit a document in place is a document app and uses `DocumentGroup` instead. Practitioners confirm the copy must happen between the two calls ([Use Your Loaf, B](https://useyourloaf.com/blog/accessing-security-scoped-files/)).

`UTType` chooses what the importer shows. `.item` accepts everything, `.content` anything with user-visible content, `.data` any byte stream; `.image`, `.movie`, `.audio`, `.pdf`, `.plainText`, `.commaSeparatedText` narrow it, and `conforms(to:)` sorts a picked file into a kind afterwards ([UTType, A](https://developer.apple.com/documentation/uniformtypeidentifiers/uttype-swift.struct)). The picker takes `allowedContentTypes: [UTType]` from the host, defaulting to `[.item]`, and records the picked type's `identifier` on the attachment so a later preview or export knows what it has. `preferredFilenameExtension` names the stored copy.

Export has two shapes. `fileExporter(isPresented:item:contentTypes:defaultFilename:onCompletion:onCancellation:)` (iOS 17) "presents a system dialog allowing the user to export a Transferable item to a file on disk", so a stored attachment exports as a `URL` ([fileExporter item, A](https://developer.apple.com/documentation/swiftui/view/fileexporter(ispresented:item:contenttypes:defaultfilename:oncompletion:oncancellation:))). The older `fileExporter(isPresented:document:...)` over `FileDocument` is marked deprecated from 27.2 with the message "Conform your document type to WritableDocument or Transferable instead"; `WritableDocument` is iOS 27 ([fileExporter document, A](https://developer.apple.com/documentation/swiftui/view/fileexporter(ispresented:document:contenttype:defaultfilename:oncompletion:)); [WritableDocument, A](https://developer.apple.com/documentation/swiftui/writabledocument)). The module uses the `item:` form and `ShareLink`, both fine on iOS 17 and not deprecated.

## Preview and sharing

Quick Look needs no UIKit on iOS 14 and later: `.quickLookPreview(_:)` "presents a Quick Look preview of the contents of a single URL" from a `Binding<URL?>`, and `.quickLookPreview(_:in:)` pages through a collection; "Quick Look updates the value of the selection binding to match the URL of the file the user is previewing. Upon dismissal by the user, Quick Look automatically sets the item binding to nil" ([quickLookPreview, A](https://developer.apple.com/documentation/swiftui/view/quicklookpreview(_:)); [quickLookPreview in, A](https://developer.apple.com/documentation/swiftui/view/quicklookpreview(_:in:))). Underneath is `QLPreviewController`, which previews "iWork documents, Microsoft Office documents, RTF, PDF files, images, text files ... CSV files, 3D models in the USDZ format", a list that "may change between operating system releases", with a title "derived from the last path component of the item URL" ([QLPreviewController, A](https://developer.apple.com/documentation/quicklook/qlpreviewcontroller)). The stored copy therefore keeps a readable name or the preview title is a UUID; see Storage. Nothing newer replaces it: no Quick Look session or API change appeared at WWDC25 in the searches run on 2026-10-31, and the modifier's and controller's pages carry no iOS 26 note (search, C). The module's `AttachmentPreview` is the SwiftUI modifier over the store's URL list; the representable the surveyed apps wrote is unnecessary on iOS 17.

Sharing is `ShareLink` (iOS 16): "The link can share any content that is Transferable", and "if you don't see a particular sharing service in the presented ShareLink, try adding a FileRepresentation to the type's Transferable conformance" ([ShareLink, A](https://developer.apple.com/documentation/swiftui/sharelink)). A stored attachment shares as its file `URL`, which Mail, Messages and AirDrop accept. For URLs "the system can automatically determine a preview", fetching the link's metadata over the network when the sheet opens; "if you provide a preview instead, the preview appears immediately without fetching data over the network" (same page). The link attachment passes its cached title and icon as the `SharePreview`, so sharing a link costs no second fetch.

## Link previews

LinkPresentation (iOS 13) has two classes. "For each metadata request, create an instance of LPMetadataProvider and call startFetchingMetadata(for:completionHandler:)"; a fetch can fail without a network, time out, be cancelled or hit an unknown `LPError` ([LPMetadataProvider, A](https://developer.apple.com/documentation/linkpresentation/lpmetadataprovider)). "The default timeout interval is 30 seconds", and `shouldFetchSubresources` ("the icon, image, or video") defaults to true ([timeout, A](https://developer.apple.com/documentation/linkpresentation/lpmetadataprovider/timeout); [shouldFetchSubresources, A](https://developer.apple.com/documentation/linkpresentation/lpmetadataprovider/shouldfetchsubresources)). `LPLinkView` "presents a link based on its available metadata ... in a familiar and consistent style", has "an intrinsic size, but it also responds to sizeToFit()", and `init(url:)` draws a placeholder before metadata arrives ([LPLinkView, A](https://developer.apple.com/documentation/linkpresentation/lplinkview)). It is a `UIView`, so it needs a `UIViewRepresentable`; practitioners wrap it and override `intrinsicContentSize` to fit a SwiftUI width ([Swiftlogic, B](https://swiftlogic-io.pages.dev/posts/LPMetadataProvider); [gist, B](https://gist.github.com/leamars/cd27fce7589ae6389847fd5375775f8d)). One provider serves one request; the module makes a new one per fetch and cancels it when the view disappears.

Caching is Apple's own instruction: "For remote URLs, cache the metadata locally to avoid the data and performance cost of fetching it from the internet every time you present it. LPLinkMetadata is serializable with NSSecureCoding" ([LPLinkMetadata, A](https://developer.apple.com/documentation/linkpresentation/lplinkmetadata)); "you don't want to do that work nor make your users pay that data and performance cost every time you present the same link" ([WWDC19 262, A](https://developer.apple.com/videos/play/wwdc2019/262/)). The store archives the metadata with `NSKeyedArchiver.archivedData(withRootObject:requiringSecureCoding: true)` under Caches, keyed by a hash of the URL, and the link `Attachment` keeps only the URL and the title. The archive includes the icon and image providers' data, which is why it lives under Caches and not in the database; if the cache is purged the view shows the placeholder and refetches on the next explicit request. `metadata.url` differs from `originalURL` after a redirect; the attachment keeps what the person typed.

Privacy is the cost the surveyed apps did not weigh. The fetch runs on the device, so the linked server learns the device's address the moment the preview is generated. The 2020 Mysk and Bakry study sorts messaging apps by who fetches: the sender's device (iMessage, Signal, WhatsApp), the receiver's device, or a server; a receiver-side fetch exposes the receiver's address "without any action by the receiver", and a server-side fetch gives the provider the link's contents, which the authors say breaks end-to-end encryption ([Mysk, B](https://mysk.blog/2020/10/25/link-previews/)). For a single-user attachment the person adding the link is the only party, so the rule is simple: fetch once, when they add it, on their action; never on scroll or on launch; cache the result; and if the app ever shows links other people sent, generate the preview on the sender's side or not at all, which is an app decision the module documents. `LPMetadataProvider` has no Low Data Mode switch, so the host can skip the fetch when `NWPathMonitor` reports a constrained path and show the placeholder.

## Storage

Apple's directory rules decide the layout. "Put app-created support files in the Library/Application Support/ directory ... files that the app uses to run but that should remain hidden from the user"; "Put data cache files in the Library/Caches/ directory ... the system may delete the Caches/ directory to free up disk space, so your app must be able to re-create or download these files as needed"; "Any file that can be re-created or downloaded must be excluded from the backup. This is particularly important for large media files" ([File System Programming Guide, A](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html)). The `Documents` folder exists to expose files through file sharing and the Files app, which an attachment store does not want. So: originals under `Application Support/Attachments/`, backed up with the database that names them, since they are the person's data and cannot be re-created; thumbnails under `Caches/Attachments/Thumbnails/` and link metadata under `Caches/Attachments/Links/`, never backed up and rebuilt on demand; captured photos written straight there, never through `tmp`. The database module already puts its store at `Application Support/<name>.store` ([DatabaseStorage](../../Modules/Database/Sources/DatabaseStorage.swift)), so one backup carries both.

The record holds a relative path, never an absolute URL: the sandbox container moves between installs and updates, so an absolute URL saved today is wrong tomorrow. The file is named by the attachment's UUID with the content type's `preferredFilenameExtension`; the display name the person saw (the picked file's `lastPathComponent`, or "Photo" with a date) is stored on the record and shown in the grid. Quick Look titles its sheet from the file's last path component, so when the preview opens the store hands Quick Look a hard link or a symlink in `tmp` with the display name, or the module accepts a UUID title in the first version and notes it. Reading file dates to sort or sweep would pull in the required-reason file timestamp API category (privacy manifest `NSPrivacyAccessedAPICategoryFileTimestamp`), so the record stores `createdAt` and `byteCount` itself and the store never asks the file system for dates ([Describing use of required reason API, A](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api)).

Thumbnails: decode small. `UIImage.preparingThumbnail(of:)` (iOS 15) exists because "when the native image size is much larger than the bounds of the view, decoding the full size image creates unnecessary memory overhead" ([preparingThumbnail, A](https://developer.apple.com/documentation/uikit/uiimage/preparingthumbnail(of:))), and ImageIO's `CGImageSourceCreateThumbnailAtIndex` with `kCGImageSourceThumbnailMaxPixelSize` ("if this key is not specified, the width and height of a thumbnail is not limited") decodes from the file without ever holding the full bitmap ([CGImageSourceCreateThumbnailAtIndex, A](https://developer.apple.com/documentation/imageio/cgimagesourcecreatethumbnailatindex(_:_:_:)); [kCGImageSourceThumbnailMaxPixelSize, A](https://developer.apple.com/documentation/imageio/kcgimagesourcethumbnailmaxpixelsize)). For anything that is not an image, `QLThumbnailGenerator.shared.generateBestRepresentation(for: Request(fileAt:size:scale:representationTypes:))` (iOS 13) returns an icon, a low-quality thumbnail or the thumbnail, the same images Files shows ([QLThumbnailGenerator, A](https://developer.apple.com/documentation/quicklookthumbnailing/qlthumbnailgenerator); [Request, A](https://developer.apple.com/documentation/quicklookthumbnailing/qlthumbnailgenerator/request)). The store generates one JPEG thumbnail per attachment at a fixed pixel size (say 300 points at the screen scale) when the attachment is added, writes it under Caches, and regenerates it when a cell asks and the cache is gone.

The database question the task asks: `@Attribute(.externalStorage)` (iOS 17) "stores the property's value as binary data adjacent to the model storage" ([externalStorage, A](https://developer.apple.com/documentation/swiftdata/schema/attribute/option/externalstorage)); Core Data's underlying flag only says the attribute "may be stored in a file external to the persistent store" ([allowsExternalBinaryDataStorage, A](https://developer.apple.com/documentation/coredata/nsattributedescription/allowsexternalbinarydatastorage)). A developer measured 80 records with one large `.externalStorage` image each: 29 MB at launch on iOS 17.5, 592 MB on iOS 18, "implying that all image data has already been loaded"; Apple's DTS engineer answered that "making the image data attribute a relationship is the way to avoid that. This has been a best practice in Core Data" ([forum 761522, B](https://developer.apple.com/forums/thread/761522)). Paul Hudson's SwiftData guide still recommends the attribute for images ([Hacking with Swift, B](https://www.hackingwithswift.com/quick-start/swiftdata/how-to-optimize-the-performance-of-your-swiftdata-apps)), so the practitioner advice is split and the measurement wins. File references avoid the question entirely, keep the store small enough that `Database.erase` and `startOver` stay fast, and give Quick Look, `ShareLink` and the thumbnail generator the URL they need without a temporary copy. The cost is consistency: a record can outlive its file or a file its record. The store's `sweep(keeping:)` takes the identifiers the app still references and removes the rest from both directories; the app runs it after `Database.erase` and on launch after a crash-safe delay, and deletes the file when it deletes the record. The implementation's tests cover placement, thumbnail generation and the sweep in a temporary directory, as the task asks.

## Accessibility

The HIG: "Describe meaningful images. If you don't describe key images in your app's content, people can't use VoiceOver to fully experience them ... describe only the information the image itself conveys", and "Exclude purely decorative images from VoiceOver" ([HIG VoiceOver, A](https://developer.apple.com/design/human-interface-guidelines/voiceover)). `accessibilityLabel(_:)` is for "a view that doesn't display text, like an icon"; "don't use the label 'Play button' because a button already has a trait that identifies it as a button" ([accessibilityLabel, A](https://developer.apple.com/documentation/swiftui/view/accessibilitylabel(_:)-5f0zj)). `Image(decorative:)` makes an image SwiftUI "ignores ... for accessibility purposes" ([init(decorative:bundle:), A](https://developer.apple.com/documentation/swiftui/image/init(decorative:bundle:))).

The system's own descriptions are a safety net, not a label. VoiceOver Recognition's Image Descriptions ("VoiceOver describes images in apps and on the web") and Text Recognition ("reads the text it identifies within images and photos") need iOS 14 and an iPhone XS or later, and the person has to turn them on under Settings, Accessibility, VoiceOver, VoiceOver Recognition ([Use VoiceOver Recognition, A](https://support.apple.com/111799)). The task's note of iOS 17 for image recognition is iOS 14 in Apple's article. The module labels every thumbnail with what it knows: the caption if the app supplies one, otherwise the kind and the display name or the date ("Photo, 31 October", "PDF, invoice.pdf", "Link, apple.com"), and groups thumbnail and caption with `.accessibilityElement(children: .combine)` so VoiceOver reads them together, the HIG's grouped example (same page). The remove control gets its own label ("Remove invoice.pdf"), and the cell carries `.isButton` for tap-to-preview.

Dynamic Type in a grid: the HIG asks apps to "support larger text sizes ... give people the option to enlarge text by at least 200 percent", with 44 by 44 points the default control size on iOS ([HIG Accessibility, A](https://developer.apple.com/design/human-interface-guidelines/accessibility)). `@ScaledMetric(relativeTo: .body)` scales a number with the text style ([ScaledMetric, A](https://developer.apple.com/documentation/swiftui/scaledmetric)), so the grid's minimum cell is a scaled metric inside `LazyVGrid(columns: [GridItem(.adaptive(minimum: cell))])`: at the default size three or four cells fit across an iPhone, at accessibility sizes one or two, and the caption under each thumbnail wraps rather than truncates. At the accessibility sizes the module switches to a one-column list where the caption sits beside the thumbnail, the pattern Photos and Files use; `dynamicTypeSize.isAccessibilitySize` is the switch. The `swiftui-accessibility-auditor` skill runs on the grid, the picker menu and the preview before the visible task closes, per `AGENTS.md`.

## Candidate API and template demo

Sketch only, not compiled Swift:

```swift
// Attachments module
public struct Attachment: Identifiable, Codable, Hashable, Sendable {
    public enum Kind: String, Codable, Sendable { case image, movie, file, link }
    public var id: UUID
    public var kind: Kind
    public var displayName: String            // "invoice.pdf", "Photo", the link's title
    public var contentType: String            // UTType identifier; "public.url" for links
    public var byteCount: Int64               // 0 for links
    public var createdAt: Date
    public var relativePath: String?          // under the store's root; nil for links
    public var url: URL?                      // links only
}

public protocol AttachmentStoring: Sendable {
    func add(copying source: URL, kind: Attachment.Kind, displayName: String) async throws -> Attachment
    func add(image: UIImage, displayName: String) async throws -> Attachment       // camera
    func add(link: URL) async throws -> Attachment                                 // fetches and caches metadata
    func fileURL(for: Attachment) -> URL?
    func thumbnail(for: Attachment, pixelSize: CGFloat) async -> UIImage?           // cached under Caches
    func linkMetadata(for: Attachment) async -> LPLinkMetadata?                     // cached under Caches
    func remove(_: Attachment) throws
    func sweep(keeping: Set<Attachment.ID>) throws -> Int                           // files removed
}
public struct AttachmentStore: AttachmentStoring {
    public init(root: URL = .applicationSupportDirectory.appending(path: "Attachments"),
                cache: URL = .cachesDirectory.appending(path: "Attachments"),
                linkTimeout: Duration = .seconds(10))
    public static func temporary() -> AttachmentStore                              // tests and previews
}

public struct CameraPermission: PermissionRequesting { }                           // Onboarding's protocol

public struct AttachmentPicker: View {                                            // the menu
    public init(store: any AttachmentStoring, sources: AttachmentSource = .all,
```

The template demo: the Database module's `TimerPresetsView` gains an attachment per preset (a photo of the drill, a PDF of the plan), which exercises the store, the SwiftData reference (`attachments: [Attachment]` as a `Codable` array on the model, or a relationship to an app-owned `@Model` wrapper), the grid, Quick Look, `ShareLink` and a link row, and gives the UI test one screen to walk: add from Photos, add a fake camera photo, add a fake link, preview, remove, screenshot. ## Remaining uncertainty

- Whether XCUITest can select a sample photo inside the out-of-process `PhotosPicker` on the iOS 27 simulator is reported workable by practitioners but undocumented; the implementation tries it first and falls back to a fake.
- The iOS 18 `.externalStorage` memory behaviour comes from one measured forum report and a DTS reply, not a document; the module avoids the attribute rather than depending on a fix.
- Quick Look's title for a UUID-named file: the documented behaviour is "derived from the last path component", so the first version either accepts it or hands Quick Look a named link in `tmp`; test both on the phone.
- No iOS 26 or 27 change to `PhotosPicker`, `QLPreviewController` or LinkPresentation turned up in searches on 2026-10-31; the `fileExporter(document:)` deprecation in 27.2 is the only version-sensitive finding, and the module does not use that form. The Mac has iOS 27.0 simulators; anything that needs a later point release runs on the `xcode-27` runner.
- The required-reason API page lists categories on sub-pages this check could not fetch; the module sidesteps the file timestamp category by never reading file dates, and the implementer confirms no other covered API (disk space, for example) is used before adding the module's privacy manifest.
- HEIC from the camera: `UIImage` from `UIImagePickerController` is re-encoded by the store (JPEG at a fixed quality, or HEIC through `CGImageDestination` with `UTType.heic`), which drops the original metadata; a photo chosen from Photos is copied as-is. Whether apps want the original camera bytes is a question for the first real app.
