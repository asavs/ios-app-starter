# Live Activities for a running session

Built as the `SessionActivity` module and the `StarterWidgets` extension target (2026-10-31, `ios-s8.3`); see [modules.md](../modules.md#sessionactivity) for what shipped and what stays with the app. Checked 2026-10-31 by claude-mac for board tasks ios-6dd.7 (this research) and ios-s8.3 (the implementation). Source grades: A = Apple documentation, HIG, WWDC session or first-party sample; B = maintained implementation, Apple engineer forum reply or practitioner experiment; C = anecdote or search snippet. A describes the contract, not proof of every OS behaviour. Recommendations are design judgments, not tested code. Apple pages were read through their `developer.apple.com/tutorials/data/<path>.json` endpoints; links point at the readable pages.

The app survey counted one app with a Live Activity for calls. On inspection that app has a `LiveActivityManager` whose three methods are `TODO` comments and no widget extension, so no surveyed app has shipped one. The timer in the template is the first.

## Recommendation

Add a Live Activity for the session timer in two parts: a `SessionActivity` module that defines the activity's attributes, its content state and the SwiftUI views for every presentation, and a `StarterWidgets` app extension target in `project.yml` that hosts them. The app starts the activity when a session starts, updates it on every transition it sees, and ends it when the session finishes. Pause and resume work from the expanded Dynamic Island and the Lock Screen through an App Intent that the system runs in the app's process. The compact presentations deep-link to the Timer tab through the existing `starterapp://timer` link.

Design around one fact: a Live Activity is a view the system archived, not running code. The system itself draws a countdown to a date, so the activity needs no update while a phase runs. Nothing in the activity can run when the phase ends, and the app is suspended in the background, so the phase label only changes when the app runs again: in the foreground, when a person taps pause or resume on the activity, or when a scheduled notification brings them back. The activity therefore shows the current phase's countdown, which the system renders, plus the session's end time, which needs no update at all, and marks itself stale at the phase end so the view can say the phase is over. Phase-change sound and the next phase's label while the phone is locked remain the job of scheduled notifications (`ios-1mo`) and, on iOS 26 and later, of AlarmKit, which runs the whole countdown system-side with sound. Those are complements, not replacements.

Two prerequisites fall out of this. The session state must be stored as wall-clock dates, since the intent that pauses the timer runs in a freshly launched app process, and `SessionClock` today anchors on a `ContinuousClock` instant that only means something inside one process. And the repository's configuration checks, symbol validation and example overlays all assume one app target and three bundle identifiers; the extension is a fourth target with a fourth identifier, and each of those scripts needs to learn about it. The account change is small: automatic signing registers one more App ID under the team, the app's identifier with a `.Widgets` suffix, and creates its development and distribution profiles. No new capability, entitlement or certificate. Asa approves that before the first signed build.

## What a Live Activity is

ActivityKit starts, updates and ends an activity from the app; a widget extension draws it. "Live Activities don't use a timeline mechanism to update their content. However, they use WidgetKit and a widget extension with a similar cycle of view archiving and decoding", and "the system can't run your code or update data bindings at the time it renders your widget" ([Adding interactivity, A](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities)). "Each Live Activity runs in its own sandbox, and, unlike a widget, a Live Activity can't access the network or receive location updates" ([Displaying live data, A](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities)). The system also owns animation: it ignores `withAnimation` and `animation(_:value:)` and uses its own timing (same page).

The static attributes and the dynamic content together "can't exceed a combined size of 4 KB"; `ActivityAuthorizationError.attributesTooLarge` is the failure ([ContentState, A](https://developer.apple.com/documentation/activitykit/activityattributes/contentstate); [attributesTooLarge, A](https://developer.apple.com/documentation/activitykit/activityauthorizationerror/attributestoolarge)). An activity "can be active for up to eight hours"; after that the system ends it, removes it from the Dynamic Island at once and leaves it on the Lock Screen for up to four more hours ([Displaying live data, A](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities)). `end(_:dismissalPolicy:)` takes a final content state and `.default` (up to four hours on the Lock Screen), `.immediate`, or `.after(Date)`, capped at four hours ([end, A](https://developer.apple.com/documentation/activitykit/activity/end(_:dismissalpolicy:)); [after, A](https://developer.apple.com/documentation/activitykit/activityuidismissalpolicy/after(_:))). The HIG asks to "end a Live Activity immediately when the task or event ends" and says a custom dismissal of "15 to 30 minutes is adequate" ([HIG Live Activities, A](https://developer.apple.com/design/human-interface-guidelines/live-activities)).

`Activity.request(attributes:content:pushType:)` works "from your app while it's in the foreground. Note that you can't do this while your app is in the background, unless you adopt AppIntents and start the Live Activity using a LiveActivityIntent"; pass `nil` for `pushType` when only the app updates it ([request, A](https://developer.apple.com/documentation/activitykit/activity/request(attributes:content:pushtype:))). `update(_:)` works from the foreground or the background, and "the system ignores attempts to update a Live Activity that ended" ([update, A](https://developer.apple.com/documentation/activitykit/activity/update(_:))). A person can turn Live Activities off per app; check `ActivityAuthorizationInfo().areActivitiesEnabled` and observe `activityEnablementUpdates` ([ActivityAuthorizationInfo, A](https://developer.apple.com/documentation/activitykit/activityauthorizationinfo)). Starting can also fail because the device "reached its limit of active and scheduled Live Activities" ([Displaying live data, A](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities)). The app's Info.plist needs `NSSupportsLiveActivities` set to true ([NSSupportsLiveActivities, A](https://developer.apple.com/documentation/bundleresources/information-property-list/nssupportsliveactivities)).

The app can die while the activity lives on: "When the app launches the next time, check if any activities are still active, update your app's stored Live Activity data, and end any Live Activity that's no longer relevant", through `Activity<Attributes>.activities` and `activityUpdates` ([Displaying live data, A](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities); [activities, A](https://developer.apple.com/documentation/activitykit/activity/activities)). A person removing the activity from the Lock Screen "ends the Live Activity, but it doesn't end or cancel the person's action that started it" (same page), so the timer keeps running in the app.

Apple documents an hourly budget only for push updates; no page fetched states a budget for local `update(_:)` calls. The HIG still says "Update a Live Activity only when new content is available" ([HIG, A](https://developer.apple.com/design/human-interface-guidelines/live-activities)). The template updates on transitions only, never on a tick.

## Modelling a countdown

`ActivityAttributes` is `Codable`; its `ContentState` is `Codable` and `Hashable`. Apple's own example keeps the order details in the attributes and puts `deliveryTimer: ClosedRange<Date>` in the content state ([ActivityAttributes, A](https://developer.apple.com/documentation/activitykit/activityattributes)). `Text(timerInterval:pauseTime:countsDown:showsHours:)` and `ProgressView(timerInterval:countsDown:label:currentValueLabel:)` are iOS 16 APIs that the system drives from the archived view, so the countdown runs with the app suspended ([Text, A](https://developer.apple.com/documentation/swiftui/text/init(timerinterval:pausetime:countsdown:showshours:)); [ProgressView, A](https://developer.apple.com/documentation/swiftui/progressview/init(timerinterval:countsdown:label:currentvaluelabel:))). `pauseTime` freezes the display at a date; the documented example counts down from 12:00 and pauses at 10:00 ([Text, A](https://developer.apple.com/documentation/swiftui/text/init(timerinterval:pausetime:countsdown:showshours:))). Date-relative progress views "don't support custom styles" ([ProgressView, A](https://developer.apple.com/documentation/swiftui/progressview/init(timerinterval:countsdown:label:currentvaluelabel:))). Request the digit animation with `contentTransition(.numericText(countsDown: true))` ([Displaying live data, A](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities)).

Apple does not document what the timer text shows after its interval ends. Practitioners report that `Text(timerInterval:)` stops at 0:00 and stays there, while `Text(_, style: .timer)` counts up past the date ([Blake Crosley, B](https://blakecrosley.com/blog/live-activities-state-machine); [forum 733305, C](https://developer.apple.com/forums/thread/733305)). Nothing in the view can end or change the activity at that moment. `ActivityContent(state:staleDate:relevanceScore:)` lets the app name the moment after which "the system considers the Live Activity out of date" and the view reads `context.isStale` ([staleDate, A](https://developer.apple.com/documentation/activitykit/activitycontent/staledate); [isStale, A](https://developer.apple.com/documentation/widgetkit/activityviewcontext/isstale)). Forum reports say the stale state is delivered to the app late and that the view only dims; treat `isStale` as a hint for the view's copy, never as a trigger ([forum 733305, C](https://developer.apple.com/forums/thread/733305); [forum 759250, C](https://developer.apple.com/forums/thread/759250)).

The surveyed implementations model pause the same way: an optional end date that is `nil` while paused, plus the remaining seconds, with a static string drawn while paused ([OneTimer, B](https://github.com/lioneldude83/OneTimer-LiveActivityIntents); [Pomly, B](https://github.com/tapariapurv/pomly)). None uses `pauseTime`. For the template, the content state carries the phase's `ClosedRange<Date>` while running and `pausedRemaining: Duration` while paused; the view switches between the system timer text and a formatted duration. A resume publishes a new range shifted by the paused time.

A multi-phase session needs more. The content state holds the phase index and count, the phase title and kind, the phase range, and the session end date. The session end is one date the system counts down to without any update, so the Lock Screen always shows a true number even when the phase label is behind. `staleDate` is the phase end; a stale running phase shows "Phase over. Open to continue" instead of a frozen 0:00. When the app returns to the foreground it publishes the current phase. For a seamless phase change while the phone is locked there are exactly three sanctioned routes: the app is running (not the case for a timer; see [background-audio.md](background-audio.md)), a push from a server, or AlarmKit on iOS 26. The template takes none of them in the first version and says so in the view.

The `SessionClock` stores a `ContinuousClock.Instant` anchor. An intent that pauses the timer runs in an app process the system launched in the background, where that anchor is meaningless. The implementation adds a wall-clock record of the session (plan, banked time, started-at date, paused flag) that the app saves on every transition and the intent reads, acts on and saves back, then updates the activity. The in-memory `SessionTimer` reloads from it when the app comes to the foreground. `Date` can jump when the clock changes; the record keeps `ContinuousClock` for the running app and uses the date only across process launches.

## Presentations and the HIG

An activity "must support: Compact, Minimal, Expanded, Lock Screen" ([HIG, A](https://developer.apple.com/design/human-interface-guidelines/live-activities)). The compact presentation is two elements either side of the camera that should "read as a single piece of information" with "similarly sized views for both leading and trailing elements" and no padding against the camera (same page). The Timer app is the HIG's own minimal example: it "displays the remaining time instead of a static icon" (same page). The expanded presentation has `leading`, `trailing`, `center` and `bottom` regions; a region's `priority` lets one view take the full width and `verticalPlacement: .belowIfTooWide` wraps leading content under the camera ([DynamicIslandExpandedRegion, A](https://developer.apple.com/documentation/widgetkit/dynamicislandexpandedregion)). The Lock Screen presentation is a banner of 84 to 160 points; "the system may truncate a Live Activity if its height exceeds 160 points" ([Displaying live data, A](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities)). On a 393-point screen the compact elements are 52.33 by 36.67 points each and the minimal 36.67 to 45 wide; the expanded and Lock Screen presentations are 371 wide ([HIG Specifications, A](https://developer.apple.com/design/human-interface-guidelines/live-activities#Specifications)).

Timer text in a widget "becomes horizontally flexible and expands to fill the available width, because its content keeps changing as the timer counts. Widgets can't perform layout again after the system archives them", so Apple says to apply a `frame(width:)` ([Text, A](https://developer.apple.com/documentation/swiftui/text/init(timerinterval:pausetime:countsdown:showshours:))). Every surveyed implementation pins the compact trailing width between 40 and 52 points with `monospacedDigit()`, and Apple's Food Truck sample uses `frame(width: 40)` ([Food Truck, A](https://github.com/apple/sample-food-truck/blob/HEAD/Widgets/TruckActivityWidget.swift)). Show hours only when the phase has them (`showsHours: false` for a 20-second interval) so the digits fit.

Colors: compact, minimal and expanded presentations have a fixed black background and take no custom background; the Lock Screen may use `activityBackgroundTint` with `activitySystemActionForegroundColor` for the dismiss button; the keyline around the island follows `DynamicIsland.keylineTint` ([HIG, A](https://developer.apple.com/design/human-interface-guidelines/live-activities); [Creating custom views, A](https://developer.apple.com/documentation/activitykit/creating-custom-views-for-live-activities)). "Use large, heavier-weight text — a medium weight or higher" and the system text styles; use `ContainerRelativeShape` for rounded elements near corners ([HIG, A](https://developer.apple.com/design/human-interface-guidelines/live-activities)). The theme's accent colours the ring and the keyline; the text stays white on the island.

Animations run at most two seconds and the system skips them on an Always-On display with reduced luminance; check `isLuminanceReduced` before anything decorative ([HIG, A](https://developer.apple.com/design/human-interface-guidelines/live-activities); [Animating data updates, A](https://developer.apple.com/documentation/widgetkit/animating-data-updates-in-widgets-and-live-activities)). Neither the HIG page nor the WidgetKit animation article mentions Reduce Motion; the system owns the transitions, so the module adds no animation of its own. The HIG Live Activities page says nothing about Activity rings; the module reuses the `TimerRing` research's stance (one ring, no imitation).

Other surfaces come for free and shape the compact design. Apple Watch shows the compact leading and trailing elements together in the Smart Stack from iOS 18; a custom small layout needs `supplementalActivityFamilies([.small])` (iOS 18) ([ActivityFamily, A](https://developer.apple.com/documentation/widgetkit/activityfamily); [WWDC24 10068, A](https://developer.apple.com/videos/play/wwdc2024/10068)). CarPlay (iOS 26) uses the same small family and disables interaction; macOS 26 shows a paired iPhone's activity in the menu bar with no code changes ([WWDC25 216, A](https://developer.apple.com/videos/play/wwdc2025/216); [WWDC25 278, A](https://developer.apple.com/videos/play/wwdc2025/278)). StandBy scales the Lock Screen presentation by two; `isActivityFullscreen` reports it ([isActivityFullscreen, A](https://developer.apple.com/documentation/swiftui/environmentvalues/isactivityfullscreen)). iOS 27 adds a reduced-width island mode (landscape, two simultaneous activities) where content must fit a 28-point circle, read from `isDynamicIslandLimitedInWidth` ([isDynamicIslandLimitedInWidth, A](https://developer.apple.com/documentation/swiftui/environmentvalues/isdynamicislandlimitedinwidth)). The first version draws a ring and a number small enough for that circle and leaves the small family for a follow-up.

The HIG also warns that activities "that appear unexpectedly can be surprising or even unwanted": start one only after a person's action and give them a way to turn it off in the app ([HIG, A](https://developer.apple.com/design/human-interface-guidelines/live-activities)). Starting the timer is that action, and a Cues-style toggle in the module's settings section turns the activity off.

## Interaction and deep links

Buttons and toggles in a Live Activity use `Button(intent:)` and `Toggle(intent:)` from App Intents, iOS 17 and later, and are allowed "in the expanded and the Lock Screen presentation" only; "on a locked device, buttons and toggles are inactive" until the person unlocks, and they do nothing in CarPlay ([Adding interactivity, A](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities)). An intent that conforms to `LiveActivityIntent` runs in the app's process: "the system launches your app process without opening the app, performs the intent" ([LiveActivityIntent, A](https://developer.apple.com/documentation/appintents/liveactivityintent)); "Make sure to add your custom app intent to your app target" ([Adding interactivity, A](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities)). The intent must update the activity itself; there is no timeline reload. Widgets do not resolve parameters, so the intent carries the session identifier as a plain stored property. The HIG asks to "prefer limiting it to a single element"; the template offers one pause/resume toggle and nothing else ([HIG, A](https://developer.apple.com/design/human-interface-guidelines/live-activities)). A tap on a button "should do more than open the app"; to open the app, use a link (same page).

Deep links: `widgetURL(_:)` serves the Lock Screen, compact and minimal presentations, and both compact elements must link to the same screen; the expanded presentation may use `Link` as well, and a `Link` takes priority over the `widgetURL` ([Launching your app, A](https://developer.apple.com/documentation/activitykit/launching-your-app-from-a-live-activity); [DynamicIsland.widgetURL, A](https://developer.apple.com/documentation/widgetkit/dynamicisland/widgeturl(_:))). The URL arrives in `onOpenURL`, which `StarterTabsView` already routes through `DeepLink.tab(in:)`, so the activity links to `starterapp://timer` and nothing else. The scheme comes from `APP_URL_SCHEME` in project.yml; the extension reads it from its own Info.plist, which the implementation sets from the same setting.

## The widget extension

Live Activity views live in a widget extension: "add code to your existing widget extension or create a new widget extension if your app doesn't already include one" ([Displaying live data, A](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities)). The extension's Info.plist declares `NSExtension` with `NSExtensionPointIdentifier` `com.apple.widgetkit-extension` ([NSExtensionPointIdentifier, A](https://developer.apple.com/documentation/bundleresources/information-property-list/nsextension/nsextensionpointidentifier)). Its entry point is a `WidgetBundle` holding an `ActivityConfiguration(for: Attributes.self)` with the Lock Screen view and a `DynamicIsland` of expanded regions plus compact and minimal views ([ActivityConfiguration, A](https://developer.apple.com/documentation/widgetkit/activityconfiguration); [WidgetBundle, A](https://developer.apple.com/documentation/swiftui/widgetbundle)). The extension's bundle identifier must be a descendant of the app's, such as `com.example.StarterApp.Widgets` ([Xcode Help, A](https://help.apple.com/xcode/mac/current/en.lproj/dev9b66ae7df.html); [DTS, forum 700818, A](https://developer.apple.com/forums/thread/700818)). Apple publishes no deployment-target rule for extensions; keep it equal to the app's.

Limits: an Apple engineer puts widget extension memory at "relatively small memory caps (~30mb)" ([forum 834384, A](https://developer.apple.com/forums/thread/834384)); an extension cannot use `UIApplication.shared`, run long tasks or talk to its app directly ([App Extension Programming Guide, A](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionOverview.html)). Image assets must fit the presentation or the activity "might fail to start" ([request, A](https://developer.apple.com/documentation/activitykit/activity/request(attributes:content:pushtype:style:))). The extension draws; it never starts an activity.

Code sharing: Apple's guidance is an embedded framework linked by both targets, with no API the extension cannot use ([Handling Common Scenarios, A](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionScenarios.html)). A Swift package product is the same thing in this repository. Attributes are encoded by type, so the attributes and content state are defined once, in the module, and both targets link it. App Groups are only for shared files and defaults; the activity's data travels in its content state, and the first version needs no group ([Configuring app groups, A](https://developer.apple.com/documentation/xcode/configuring-app-groups)). Two surveyed implementations do use a group so the intent and the widget share state; the template keeps the intent's state in the app's own container, since the intent runs in the app.

The package builds on the Mac host for `swift test`. WidgetKit exists on macOS; ActivityKit does not. The module wraps its ActivityKit-dependent types in `#if canImport(ActivityKit)` and defines the content state and the snapshot-to-state mapping as plain `Codable` values outside the guard, so the mapping has host tests and the views compile only for iOS.

XcodeGen: a target of `type: app-extension`, `platform: iOS`, with `info:` writing the `NSExtension` dictionary and `PRODUCT_BUNDLE_IDENTIFIER` set explicitly (the `bundleIdPrefix` default would make a sibling identifier, not a child). The app lists `- target: StarterWidgets` under `dependencies`; `embed` defaults to true for an application target, and the generator copies extension dependencies into an "Embed Foundation Extensions" phase at the PlugIns folder ([ProjectSpec, B](https://github.com/yonaskolb/XcodeGen/blob/master/Docs/ProjectSpec.md); [PBXProjGenerator, B](https://github.com/yonaskolb/XcodeGen/blob/master/Sources/XcodeGenKit/PBXProjGenerator.swift)). The app's Info.plist gets `NSSupportsLiveActivities: true` under `info.properties`.

Previews: `#Preview(as: .dynamicIsland(.compact), using: attributes) { widget } contentStates: { [...] }` renders each presentation in the canvas on iOS 17 ([Previewing widgets and Live Activities, A](https://developer.apple.com/documentation/widgetkit/previewing-widgets-and-live-activities-in-xcode)). Xcode 27's preview snapshot tool "supports specifying timelines for Widgets and toggle states for Live Activities" ([Xcode 27 release notes, A](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes)).

## Signing, CI and this repository

Live Activities need no capability, entitlement or App Store Connect setting; only the Info.plist key. The push route does: "start by adding the Push Notifications capability to your app", with a server that talks to APNs and an hourly budget the system enforces ([ActivityKit push notifications, A](https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications)). The template stays off that route; it is noted for the API-key relay research (`ios-s9.1`).

What a signed build changes in the Apple account: Xcode automatic signing with `-allowProvisioningUpdates` registers an explicit App ID for the extension's bundle identifier (the app's identifier plus `.Widgets`) and creates a development provisioning profile for it on the first `run-on-device` build and an App Store profile on the first TestFlight export. It reuses the existing development and distribution certificates. Nothing is revoked and no capability is added. The template's own `com.example.StarterApp.Widgets` is never registered; the demo identity gets its own `.Widgets` descendant. Present this to Asa before the first signed build and record it in `docs/human-steps.md` (permission category `apple-provisioning`). Pull-request builds stay unsigned: `CODE_SIGNING_ALLOWED=NO` applies to every target, and the simulator lane's ad hoc identity signs the extension like the app.

What the repository rejects today, each to be extended in the implementation, in this order:

1. `scripts/check-configuration.py` requires the target set to be exactly `StarterApp`, `StarterAppTests` and `StarterAppUITests`, and checks every target's identifier, team, deployment minimum and platforms. It gains an optional `StarterWidgets` app-extension target whose identifier must be a child of the app's and whose other settings match the app.
2. `scripts/collect-release-symbols.py` raises on a `PlugIns` folder: "Embedded extensions/frameworks require additional symbol validation." It validates the extension's dSYM against the embedded `.appex` the same way it does the app.
3. `examples/pocket-notes.yml` and `examples/starter-app-demo.yml` override three bundle identifiers; they override the fourth.
4. `scripts/testflight-release.py` compares the app's Info.plist only; the archive check should also confirm the extension's identifier is a descendant.
5. `scripts/check-modules.py` compares the package's platforms with the app's; the extension target's deployment target joins that check.
6. `docs/ci.md` says the check "rejects entitlement files and enabled account capabilities"; that stays true, since this feature needs neither.

## Alternatives and complements

Scheduled local notifications are Apple DTS's recommendation for a timer whose app is suspended, with their own limits ([background-audio.md](background-audio.md); [DTS, A](https://developer.apple.com/forums/thread/132078)). They cover the phase change sound and bring the person back to the app, which then refreshes the activity. `ios-1mo` measures them on the phone.

AlarmKit (iOS 26) "create[s] custom alarms and timers in your app", with countdowns that pause and resume, and "overrides both a device's focus and silent mode" ([AlarmKit, A](https://developer.apple.com/documentation/alarmkit); [Scheduling an alarm, A](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit)). It requires `NSAlarmKitUsageDescription`, a person's authorization, and, for a countdown, a widget extension: "AlarmKit expects a widget extension if an app supports a countdown presentation. Otherwise, the system may unexpectedly dismiss alarms and fail to alert" (same page). The widget receives `AlarmAttributes<Metadata>` and draws countdown and paused presentations from a system-managed state ([AlarmAttributes, A](https://developer.apple.com/documentation/alarmkit/alarmattributes); [WWDC25 230, A](https://developer.apple.com/videos/play/wwdc2025/230)). One countdown per alarm, so an interval session would schedule one alarm per phase or re-schedule at each boundary. Pomly does exactly this with an ActivityKit fallback when alarms are denied ([Pomly, B](https://github.com/tapariapurv/pomly)). For the template, AlarmKit is the right iOS 26 example overlay once the extension exists; it is not the iOS 17 baseline.

Scheduled Live Activities (iOS 26) start at a date with a required alert ([request with start, A](https://developer.apple.com/documentation/activitykit/activity/request(attributes:content:pushtype:style:alertconfiguration:start:))); they do not solve the phase change either, since an activity is one presentation per request. Keeping the app alive with silent audio or location monitoring to update at zero, as one surveyed sample does, is the review risk `background-audio.md` describes; the template does not do it.

## Open source, graded

- **Apple Food Truck** (A, MIT, 2023): one `ClosedRange<Date>` in the content state, `Text(timerInterval:)` with a 40-point frame in the compact trailing view, start with a stale date two minutes out, end `.immediate` found through `Activity.activities`. The smallest correct shape; no pause ([source](https://github.com/apple/sample-food-truck)).
- **Apple Emoji Rangers** (A, WWDC23): a health bar rather than a timer, and the only Apple sample showing reattach through `activities`, observation of `contentUpdates`, `activityStateUpdates` and `pushTokenUpdates`, and all three dismissal policies ([page](https://developer.apple.com/documentation/widgetkit/emoji-rangers-supporting-live-activities-interactivity-and-animations)).
- **OneTimer / MyChronoPro** (B, GPL-3.0, shipping app): single countdown with pause, resume and cancel as `LiveActivityIntent` buttons; content state `endTime: Date?`, `isPaused`, `adjustedRemainingTime`; static string while paused; compact trailing `lineLimit(1).minimumScaleFactor(0.65).frame(width: 52)`. Read for the intent flow, copy nothing (GPL) ([source](https://github.com/lioneldude83/OneTimer-LiveActivityIntents)).
- **Pomly** (B, MIT, iOS 26, 2026-10): AlarmKit-first Pomodoro with an ActivityKit fallback; content state `end: Date?`, `remaining`, `total`; date-based engine that "stores endDate, never counts down"; `supplementalActivityFamilies([.small])`; tests ([source](https://github.com/tapariapurv/pomly)).
- **Wav** (B, MIT, iOS 17, Swift Testing with fakes): count-up timer whose `LiveActivityController` is an actor with a fake session for tests, the one surveyed project that tests the controller; its widget reads a shared store to cover intent updates the app has not seen ([source](https://github.com/eddmann/Wav)).
- **SwiftPizza** (B, MIT, 420 stars): both `Text(timerInterval:)` and `ProgressView(timerInterval:)`; shows why `TimelineView` is useless once locked; its keep-alive hack for the zero moment is what the template avoids ([source](https://github.com/1998code/iOS16-Live-Activities)).
- **LoopFollow** (B): renews an activity at 7.5 hours by requesting the new one before ending the old `.immediate` ([PR 539](https://github.com/LoopFollow/LoopFollow/pull/539)). Sessions in the template are far shorter; noted for an app that runs all day.

Pitfalls these report that the design already answers: compact timer text stretching unless framed (Apple's own note plus [forum 834337, B](https://developer.apple.com/forums/thread/834337)); the countdown freezing at 0:00 with no way to react from the view; `isStale` arriving late; `ActivityAuthorizationError.visibility` when starting from the background without an intent ([visibility, A](https://developer.apple.com/documentation/activitykit/activityauthorizationerror/visibility); [DTS, forum 818467, A](https://developer.apple.com/forums/thread/818467)); and the only background update path being push ([Apple engineer, forum 776031, B](https://developer.apple.com/forums/thread/776031)).

## Testing

Apple documents nothing about UI-testing a Live Activity or reading the Dynamic Island from XCUITest. Practitioners assert on `Activity<Attributes>.activities` from inside the app and keep screenshots as the evidence for the island ([Interval-Timer PR 5, B](https://github.com/MrMallon/Interval-Timer/pull/5); [agent-device issue 1296, B](https://github.com/callstack/agent-device/issues/1296)). Simulators do render the island on devices that have one; Xcode 14.1's notes fixed a bug where "iOS simulators may stop showing Live Activities and Dynamic Island features" ([Xcode 14.1 release notes, A](https://developer.apple.com/documentation/xcode-release-notes/xcode-14_1-release-notes)).

Plan: host and simulator unit tests for the snapshot-to-content-state mapping (phase range, paused remaining, session end, stale date) and for the wall-clock session record round trip; a unit test of the intent handler against a fake activity session, as Wav does; one UI test that starts a session, reads an activity count the app exposes under the UI-testing launch argument, pauses from the app and checks the count stays one, and attaches a full-screen `XCUIScreen.main.screenshot()` so the island is on record; the phone for the real check (lock, Dynamic Island long-press, pause from the island, StandBy). `Activity.request` throws `visibility` or `denied` in some test environments; the model treats a failed start as "no activity" and the UI test skips the count when `areActivitiesEnabled` is false.

## Candidate API and template demo

```swift
// SessionActivity module
public struct SessionActivityState: Codable, Hashable, Sendable {
    public var phaseIndex: Int, phaseCount: Int

    public var pausedRemaining: Duration?     // set while paused
    public var sessionEnd: Date
    public var isFinished: Bool

    init(_ snapshot: SessionSnapshot, plan: SessionPlan, now: Date)   // the mapping, host-tested

    public typealias ContentState = SessionActivityState
}
@MainActor public final class SessionActivityController {            // app side
    public init(isEnabled: @escaping () -> Bool)                     // the module's settings toggle
    public func sessionDidChange(_ snapshot: SessionSnapshot, plan: SessionPlan)   // start, update, end
    public func reattach()                                           // on launch
}

```

The app (`StarterApp/StarterWidgets/`) ships a `WidgetBundle` that lists `SessionActivityWidget`, a `ToggleSessionIntent: LiveActivityIntent` in the app target that loads the wall-clock session record, flips it and updates the activity, and the `-liveActivity.count` readout for UI tests. Settings gets the module's toggle through the `SettingsLink` convention. When the Timer tab moves to the example overlay (`ios-6dd.10`), the extension and the intent move with it; the module stays in the library.

## Remaining uncertainty

- The behaviour of `Text(timerInterval:)` after the interval ends is undocumented; verify on iOS 17 and 27 simulators and the phone.
- The lag between a phase's `staleDate` and the view seeing `isStale` is reported, not documented; measure it on the phone with the screen locked.
- Whether a `LiveActivityIntent` performed from the Lock Screen launches the app in time to read the session record on a cold start is undocumented; the surveyed apps do it, so expect it to work and test it.
- The 30 MB extension memory figure comes from an Apple engineer's forum reply, not a document; keep the extension's views free of large images.
- iOS 26 and 27 behaviours (Mac menu bar, limited-width island, AlarmKit) can only be checked on the `xcode-27` runner or a device running them; the Mac has iOS 27.0 simulators and the phone runs iOS 26.
